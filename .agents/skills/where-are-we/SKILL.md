# Where Are We

対象: $ARGUMENTS (省略時は会話で進めている作業)。

## 確認

会話の依頼・合意した範囲・完了条件を基準に、計画やタスクの状態と直近の成果を照合する。会話だけでは現在の状態が分からない箇所に限り、成果物・実行結果・関連 issue / PR・委譲先の状態を確認する。

今回の作業が全体の一部なら、会話で示された上位目標・計画・親 issue / Epic に照らし、全体の工程と今回の作業の位置づけを確認する。全体計画が不明ならその旨を示し、確認できる依頼範囲と分ける。説明のために未合意の工程を作らない。

- 実施予定、実施中、完了、未検証を区別する。最後の報告だけで、その後も処理が動いていると断定しない。
- 作業が判断待ちであることと、処理が稼働しているかを分ける。未着手・未実施の理由や待ち条件を推測しない。
- コード修正・PR のマージ・本番反映など、目的の達成までに必要な段階を分ける。途中の成功を全体の完了として扱わない。
- 別作業の差分や既存課題を今回の進捗に混ぜない。根拠のない進捗率や残り時間を作らない。

## 報告

最初に全体目標と主な工程を短い一覧や矢印で示し、完了・現在地・残りが分かるようにする。並行作業や依存関係を直列の工程に変えず、今回の作業がどの工程に属するかも示す。全体計画が不明なら工程図を作らず、分かる範囲を明記する。

続けて、必要な項目だけ簡潔に示す。

- **完了**: 達成済みの結果と、その確認根拠。
- **実施中**: 現在取り組んでいる内容。処理の稼働を未確認なら、その旨を明記する。
- **残り・待ち**: 完了条件までに残る作業、判断・外部対応待ちと再開条件。

作業の履歴やツール操作を時系列に並べない。未着手・判断待ち・完了済みなら、その状態を明記する。新しい計画や改善提案は求められた場合だけ示す。

報告のために作業状態を変更しない。進行中の依頼は、状況を聞かれただけで中止・保留にしない。
