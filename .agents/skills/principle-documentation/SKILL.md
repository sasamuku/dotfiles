# Documentation

ドキュメントには、コードや設定から読み取れない判断、制約、理由だけを載せる。

コードから読み取れることを書くと、同じ事実を 2 か所で持つことになる。コードが変わるとドキュメントだけが古くなり、読者に誤りを教える。古くなったドキュメントは、無いより悪い。

## 適用範囲

リポジトリに置く開発者向けのドキュメント、エージェント向けの指示ファイル (AGENTS.md、CLAUDE.md)、コードコメントに当てはまる。

例外が 2 つある。

- **利害関係者に向けた仕様書**: データモデルや状態遷移などは、コードと重なっても書いてよい。読者がコードを読まないからである。
- **ナビゲーションのための索引**: 読者が目的の文書にたどり着くためのディレクトリの一覧は、構成を写していても残してよい。

## 載せるもの

- **使い分けとその理由**: 選択肢が複数あるときに、どれをいつ使うか、なぜそうするか。
- **反直感的な決まり**: 一般的なやり方や既定と違う慣習。
- **やってはいけないこと**: アンチパターンと、その理由。
- **正確なコマンド**: ビルド、テスト、lint の実行方法をフラグまで正確に書き、期待される出力も添える。
- **運用の手順**: コードには現れない操作の手順。コマンドの実行例を添える。
- **設計判断の経緯**: なぜこの方式を選んだか、何と比べたか。
- **実測した数値**: 性能の基準やメモリ使用量など、測って得た値。

## 載せないもの

| 載せないもの | 正になるもの |
|---|---|
| システムの動作の説明 | コード |
| 技術スタックの一覧 | `package.json` などの依存の定義 |
| ディレクトリ構成 | リポジトリそのもの |
| 手書きの API 仕様 | OpenAPI などのスキーマ |
| 外部仕様や公式ドキュメントの転記 | 元の資料へのリンク |
| 設定値の写し | 設定ファイル |
| 完了した計画 | 計画どおりに書かれたコード |
| 他の文書と同じ内容 | 元の文書 |
| 「きれいなコードを書く」のような自明な指示 | 不要 |

## 判断の観点

- **読者にとっての価値**: 残すか迷ったら、「これが無くなったとき、読者は正しく判断できるか」「消したら誰かが困るか」を問う。この原則の文言に形式的に当てはまるかではなく、読者にとっての価値で決める。
- **文章より仕組み**: lint、型、CI、hook で強制できる決まりは、ドキュメントではなく仕組みで守らせる。必ず守らせたい決まりほど、文章に頼らない。
- **正は 1 か所**: 同じ内容を複数の場所に書かない。置き場所は既存の分類に寄せる。新しい分類が正当なのは、既存のどれにも当てはまらず、複数の文書が集まる見込みがあり、既存との境界を一言で言えるときである。
- **1 つの文書で完結**: 読者が他の文書を行き来しなくても分かるのがよい。参照は最小限にする。
- **増えるほど矛盾する**: ドキュメントは放っておくと増え、互いに矛盾し始める。価値の無くなったものは消してよい。

## 書き方

- 冗長な説明、過剰な例、自明な補足は要らない。
- 重要な決まりとコマンドが前にあると、読者は迷わない。
- 短いコード例 (Good と Bad の比較、アンチパターン) は、判断の基準を示すので、その場に書いてよい。
- まとまった実装例は写さず、既存コードのパスで示す。写した例は、元のコードが変わると古くなる。

## 事例

| 悪い例 | 良い例 |
|---|---|
| 「この API はユーザーを ID で取得して返す」と動作を説明する | 「管理画面からの操作は、RLS を通さず Admin モードを使う。テナントをまたいで参照するため」と使い分けと理由を書く |
| テストの書き方を公式ドキュメントから写す | 「テストは実 DB を使い、外部サービスだけをモックする」と、このプロジェクトに固有の決まりを書く |
| `// ユーザーを取得する` と、関数名の言い換えをコメントにする | `// 退会済みも含める。請求の再計算で参照するため` と、コードに現れない理由を書く |
