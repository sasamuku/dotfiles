# Product docs

製品開発の文書は、答える問いで層に分ける。なぜ作るかを Product Brief に、何を求めるかを PRD に、どう作るかを Design Doc に書く。

PRD に書くのは要求で、要件ではない。要求は、利用者や事業が実現したいことを使う側の言葉で書いたものである。要件は、その要求を満たすためにシステムが備える、検証できる条件である。要求を要件に落とす作業は、Design Doc で行う。

問いごとに、読み手と変わる速さが違う。1 つの文書に混ぜると、長く使う判断が、すぐ変わる詳細に埋もれる。

## 階層

| 文書 | 答える問い | 見直すとき |
|---|---|---|
| Product Brief | なぜ作るか | 製品の方向が変わるとき |
| PRD | 何を求めるか | 開発段階が進むとき、要求が変わるとき |
| Design Doc | どう作るか | 機能や開発ごと |

層の外に、次の 2 つがある。

- **ADR**: 技術の決定を 1 つずつ記録する。
- **Issue**: 誰がいつ何をするかを書く。進み具合や、ある時点の状況はここに置き、上の 3 つには書かない。

## 配置

対象プロジェクトに文書の配置が無ければ、次のように置く。

```
docs/
├── product/                               なぜ作るか、何を求めるか
│   ├── product-brief.md
│   └── product-requirements-document.md
└── engineering/                           どう作るか、何を採用したか
    ├── design-docs/
    │   └── 0001-<名前>/README.md
    └── adr/
        └── 0001-<名前>.md
```

- **分類は必要になってから足す**: `product/` と `engineering/` に収まらない文書の分類は、必要になったときに足す。
- **記録とリファレンスを分ける**: Design Doc と ADR は書いた時点の判断の記録で、実装後は直さない。いまの構成を説明する文書が必要になったら、`engineering/architecture/` に主題ごとに置き、書き換えて使う。
- **Product Brief は 1 つだけ置く**: 版にせず、書き換えて使う。
- **PRD は版ごとに 1 ファイルにする**: 版が 1 つのあいだは `product-requirements-document.md` を置き、書き換えて使う。版が分かれたら `product-requirements-document/` の下に `v1.md`、`v2.md` と並べる。版を切る基準は依頼者が決める。開発段階ごとでも、製品の大きな更新ごとでもよい。前の版は記録として残す。Design Doc から PRD を参照するときは、対応する版を指す。
- **Design Doc と ADR は雛形から作る**: 雛形は [assets/docs/engineering](assets/docs/engineering) にある。採番とステータスは、雛形の `AGENTS.md` に従う。

## 適用範囲

- 対象プロジェクトに既存の文書体系があれば、それを優先する。呼び名は組織によって違い、要件まで含めた文書を PRD と呼んで Product Brief を置かない組織も多い。名前ではなく、答える問いで対応づける。
- 全体が 1〜2 画面に収まる小さな製品では、Product Brief と PRD を 1 つにまとめてよい。そのときは、Product Brief に当たる内容を前に置く。

## 判断の観点

- **問いで置き場所を決める**: 書こうとしている内容が「なぜ」「何を求めるか」「どう作るか」のどれに答えるかで、文書を選ぶ。1 つの文書が 2 つの問いに答え始めたら、分ける。
- **参照は上の層へ向ける**: 下の層は上の層を参照する。上の層は、下の層や Issue を根拠にしない。上の層ほど長く残るので、短命なものを指すと、リンクと根拠が先に古くなる。
- **上の層を先に直す**: 要件や設計の検討で要求が変わるときは PRD を、要求の検討で方向が変わるときは Product Brief を、先に直すか同じ変更で直す。
- **セクションを埋めない**: 書くことが決まっていないセクションは作らない。どの製品にも当てはまる原則や、中身の決まっていない成功指標が、埋めるための記述になりやすい。決まっていないことは、未決の判断として挙げる。
- **推測には「（案）」と付ける**: 依頼者の説明にも既存の文書にも根拠が無く、書き手が推測で補った記述には、その場に「（案）」と付ける。印が無いと、読み手は根拠のある記述と書き手の推測を見分けられず、推測が決定として使われる。確かめて確定したら印を外す。「（案）」が残っている文書は、正式な文書として main にマージしない。

## Product Brief

セクションの並びと、各セクションに書くことは、[雛形](assets/docs/product/product-brief.md) に従う。

課題、ビジョン、ステップは、互いの言い換えになりやすい。1 つの事実は 1 つのセクションにだけ置き、全体を要約するセクションは作らない。

## PRD

セクションの並びと、各セクションに書くことは、[雛形](assets/docs/product/product-requirements-document.md) に従う。

セクションは [productboard の PRD の項目](https://www.productboard.com/glossary/product-requirements-document/) に沿っている。同じ資料にある関係者、リリース計画、リスク、制約は載せない。要求は同じ資料に無いセクションで、スコープの項目ごとに求めることを書くために足している。

## Design Doc

機能の設計も、全体の構成や移行の設計も、Design Doc として書く。セクションの並びと、各セクションに書くことは、[雛形](assets/docs/engineering/design-docs/TEMPLATE/README.md) に従う。

設計の前に、要件を書く。満たす条件が言葉になっていないと、案の比較も、完了の判定もできない。要件の出どころは PRD の要求でも、Issue でも、依頼でもよい。設計には要件をどう満たすかを書き、要件そのものは写さない。

機能をまたぐ要件は、全体の構成を決める Design Doc に書く。品質に関わる要件と、開発段階の受入条件がこれに当たる。1 つの機能に収まる要件は、その機能の Design Doc に書く。

## ADR

技術の決定 1 つを 1 件で記録する。対象は、あとから「なぜこうなっているのか」を問われる決定である。フロントエンド、バックエンド、インフラのどの層の決定も、それらをまたぐ決定も書ける。セクションの並びと、各セクションに書くことは、[雛形](assets/docs/engineering/adr/TEMPLATE.md) に従う。合意した ADR は書き換えない。方針が変わったら、新しい ADR で置き換える。Design Doc を書く中で生まれた、機能をまたぐ決定は、ADR に切り出して Design Doc から参照する。
