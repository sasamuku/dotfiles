# Product docs

製品開発の文書は、答える問いで層に分ける。なぜ作るかを Product Brief に、何を求めるかを PRD に、どう作るかを Design Doc に書く。

PRD に書くのは要求で、要件ではない。要求は、利用者や事業が実現したいことを使う側の言葉で書いたものである。要件は、その要求を満たすためにシステムが備える、検証できる条件である。要求を要件に落とす作業は、Design Doc の前半で行う。

問いごとに、読み手と変わる速さが違う。1 つの文書に混ぜると、長く使う判断が、すぐ変わる詳細に埋もれる。

## 階層

| 文書 | 答える問い | 見直すとき |
|---|---|---|
| Product Brief | なぜ作るか | 製品の方向が変わるとき |
| PRD | 何を求めるか | 開発段階が進むとき、要求が変わるとき |
| Design Doc | どう作るか | 機能や開発ごと |

層の外に、次の 2 つがある。

- **ADR**: 技術の決定を 1 つずつ記録する。
- **Issue**: 誰がいつ何をするかを書く。進み具合や、ある時点の状況はここに置き、上の 3 つには書かない。

## 配置

対象プロジェクトに文書の配置が無ければ、次のように置く。

```
docs/
├── product/                               なぜ作るか、何を求めるか
│   ├── product-brief.md
│   └── product-requirements-document.md
└── engineering/                           どう作るか、何を採用したか
    ├── design-docs/
    │   └── 0001-<名前>/README.md
    └── adr/
        └── 0001-<名前>.md
```

- **分類は必要になってから足す**: `product/` と `engineering/` に収まらない文書の分類は、必要になったときに足す。
- **記録とリファレンスを分ける**: Design Doc と ADR は書いた時点の判断の記録で、実装後は直さない。いまの構成を説明する文書が必要になったら、`engineering/architecture/` に主題ごとに置き、書き換えて使う。
- **Product Brief は 1 つだけ置く**: 版にせず、書き換えて使う。
- **PRD は版ごとに 1 ファイルにする**: 版が 1 つのあいだは `product-requirements-document.md` を置き、書き換えて使う。版が分かれたら `product-requirements-document/` の下に `v1.md`、`v2.md` と並べる。版を切る基準は依頼者が決める。開発段階ごとでも、製品の大きな更新ごとでもよい。前の版は記録として残し、Design Doc の要件には、対応する版を示す。
- **Design Doc と ADR は雛形から作る**: 雛形は [assets/docs/engineering](assets/docs/engineering) にある。採番とステータスは、雛形の `AGENTS.md` に従う。

## 適用範囲

- 対象プロジェクトに既存の文書体系があれば、それを優先する。呼び名は組織によって違い、要件まで含めた文書を PRD と呼んで Product Brief を置かない組織も多い。名前ではなく、答える問いで対応づける。
- 全体が 1〜2 画面に収まる小さな製品では、Product Brief と PRD を 1 つにまとめてよい。そのときは、Product Brief に当たる内容を前に置く。

## 判断の観点

- **問いで置き場所を決める**: 書こうとしている内容が「なぜ」「何を求めるか」「どう作るか」のどれに答えるかで、文書を選ぶ。1 つの文書が 2 つの問いに答え始めたら、分ける。
- **参照は上の層へ向ける**: 下の層は上の層を参照する。上の層は、下の層や Issue を根拠にしない。上の層ほど長く残るので、短命なものを指すと、リンクと根拠が先に古くなる。
- **上の層を先に直す**: 要件や設計の検討で要求が変わるときは PRD を、要求の検討で方向が変わるときは Product Brief を、先に直すか同じ変更で直す。
- **セクションを埋めない**: 書くことが決まっていないセクションは作らない。どの製品にも当てはまる原則や、中身の決まっていない成功指標が、埋めるための記述になりやすい。決まっていないことは、未決の判断として挙げる。
- **推測には「（案）」と付ける**: 依頼者の説明にも既存の文書にも根拠が無く、書き手が推測で補った記述には、その場に「（案）」と付ける。印が無いと、読み手は根拠のある記述と書き手の推測を見分けられず、推測が決定として使われる。確かめて確定したら印を外す。「（案）」が残っている文書は、正式な文書として main にマージしない。

## Product Brief

セクションは次の順に置く。全体で 1〜2 ページに収める。

1. **背景**: 誰が提供し、どの事業の文脈にある製品か。
2. **解く課題**: 誰の、どんな課題か。使う人と導入を決める人が違うときは、分けて書く。響くものが違うので、片方だけを見て作ると、もう片方に選ばれない。
3. **ビジョン**: 目指す状態を 1〜2 文で書く。
4. **目指す姿までのステップ**: どの順に、誰に、何ができるようになるか。解決策の詳細は書かない。
5. **製品として目的にしないこと**
6. **まだ決まっていないこと**: 方向に関わる未決の判断。
7. **関連文書と更新のしかた**: 各層の文書の場所と役割。すでにある文書だけを載せる。

課題、ビジョン、ステップは、互いの言い換えになりやすい。1 つの事実は 1 つのセクションにだけ置き、全体を要約するセクションは作らない。

## PRD

セクションは [productboard の PRD の項目](https://www.productboard.com/glossary/product-requirements-document/) に沿い、次の順に置く。同じ資料にある関係者、リリース計画、リスク、制約は載せない。要求は同じ資料に無いセクションで、スコープの項目ごとに求めることを書くために足している。

1. **目的**: この開発段階で、なぜ作るか。解く課題に結びつけて書く。
2. **成功の指標**: 利用者に価値が届いたかを示す指標。数値には、根拠と合意先を添える。
3. **利用者**: 誰のためのものか。誰のためのものでないか。
4. **スコープ**: この開発段階で作るものと作らないものを、機能やユーザーストーリーの単位で挙げる。
5. **要求**: スコープの各項目について、利用者や事業が求めることを、使う側の言葉で書く。できること (機能) に加えて、どんな状態でなければならないか (品質) も書く。たとえば「ほかの会社の情報は見えない」「情報が古いときは、古いと分かる」。優先度を付ける。受入条件や数値の水準といった検証できる条件は書かず、Design Doc の要件で決める。
6. **デザインとワイヤーフレーム**: 解決策の全体像が分かる、画面の流れやワイヤーフレーム。デザインハーネスや `DESIGN.md` など、画面の決まりを別に持っている場合は省いてよい。
7. **前提**: 解決策が頼っている、まだ確かめていない前提。確認先と、外れたときに実装を止める条件を書く。止める条件に当たらない作業は進められる。
8. **依存**: この開発が成り立つために、先に済んでいる必要があるもの。

## Design Doc

機能の設計も、全体の構成や移行の設計も、Design Doc として書く。前半に要件、後半に設計を書く。

- **要件**: PRD の要求を、検証できる条件に落とす。どの要求に対応するかを示し、機能要件 (利用者ができること) と非機能要件 (どの水準で満たすか) を分ける。それぞれに変えない ID と受入条件を付け、受入条件には検証方法を、数値には根拠と合意先を添える。
- **設計**: 要件を ID で参照し、要件そのものは写さない。

機能をまたぐ要件は、全体の構成を決める Design Doc に書く。品質の要求から落とした要件と、開発段階の受入条件がこれに当たる。1 つの機能に収まる要件は、その機能の Design Doc に書く。

## ADR

技術の決定 1 つを 1 件で記録する。対象は、あとから「なぜこうなっているのか」を問われる決定である。フロントエンド、バックエンド、インフラのどの層の決定も、それらをまたぐ決定も書ける。背景、検討した選択肢、決定、その結果を書く。合意した ADR は書き換えない。方針が変わったら、新しい ADR で置き換える。Design Doc を書く中で生まれた、機能をまたぐ決定は、ADR に切り出して Design Doc から参照する。
