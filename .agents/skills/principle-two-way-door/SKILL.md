# Two-way door

決定には 2 種類ある。くぐった先が気に入らなくても引き返せるもの (Two-way door) と、くぐったら元の場所に戻れないもの (One-way door) である。

- **One-way door**: 影響が大きく、元に戻せないか、ほぼ戻せない決定。時間をかけ、関係する人と相談して、慎重に決める。
- **Two-way door**: 変えられる、元に戻せる決定。まずい選択をしても、その結果を長く抱えずに済む。判断できる個人か小さなチームが、速く決める。

ほとんどの決定は Two-way door である。

## 見分ける観点

- **元の場所に戻れるか**: 問うのは、失敗を直せるかではなく、決定する前の状態に戻れるかである。直す手段があっても、戻るまでの間に起きたことが消えないなら、元の場所には戻れていない。
- **戻すのにいくらかかるか**: 戻せるかは 0 か 1 ではない。戻す負担が大きいほど、One-way door に近づく。
- **影響は大きいか**: One-way door は、影響が大きく、かつ戻せない決定である。戻せなくても影響が小さいなら、慎重に扱う必要はない。
- **状況で変わる**: 同じ種類の変更でも、誰が影響を受けるか、戻す手段が用意されているかで、扉の向きが変わる。
- **時間で変わる**: その場では戻せても、人やコードが頼り始めると、戻す負担は日ごとに増える。

## 見誤ったときの失敗

どちらに見誤っても失敗する。

- **Two-way door を One-way door として扱う**: 重い進め方をすべての決定に使い、遅くなる。考えずにリスクを避け、試す回数が減り、新しいものが生まれなくなる。組織が大きくなるほど、この失敗に傾く。
- **One-way door を Two-way door として扱う**: 戻れない決定を、軽く決めてしまう。

## 決める時機

- **Two-way door はできるだけ早く決める**: 情報が揃うのを待たない。決めて、結果を見て、直す。速く決めてよいことは、雑に決めてよいことではない。
- **One-way door はできるだけ遅く決める**: 決める必要が出るまで、選択肢を残す。戻れない部分を切り離し、最後に回せないかを考える。たとえば、消す前に退避する、段階に分けて戻れない一手を最後にする、新旧を並べてから切り替える。

## 事例

ソフトウェア開発での例。同じ種類の変更でも、状況で扉の向きが変わる。

| 対象 | Two-way door のとき | One-way door のとき |
|---|---|---|
| アプリのデプロイ | 利用者がまだいない。または、前の版にすぐ戻せて、データの形を変えない | 利用者がいて、データの形を変える。または、戻す手段が無い |
| DB のスキーマ変更 | 列やテーブルの追加。データの無い環境への適用 | データのある環境での、列の削除や型の変更 |
| データの削除 | 作り直せる開発用のデータ | バックアップの無い本番のデータ |
| インフラの変更 | 作り直せるリソースの追加や設定の変更 | データを持つリソース (DB、ストレージ) の削除や置き換え |
| ブランチの書き換え | 自分だけが使うブランチへの force-push | 他の人も使うブランチへの force-push |
| 依存の更新 | パッチ、マイナー | メジャー |
| ライブラリの採用 | 1 か所で試す。差し替えやすい境界の内側で使う | 基盤として全体で使い始める (ORM、UI フレームワーク、認証基盤) |
| インターフェース | 内部の関数やモジュールの名前と形 | 外部に公開している API、スキーマ、ファイル形式 |
| 外への発信 | 下書き、自分だけが見る場所への書き込み | チャット、メール、Issue や PR へのコメント。相手が読んだ時点で戻れない |
| 認証と認可 | 利用者のいない環境での変更。本番でも、権限を狭める変更 | 本番で権限を広げる、認証を通らない経路を作る変更。その間に見られたデータは戻らない。利用者の移行を伴う認証基盤の乗り換え |
| 秘密情報 | 手元の `.env` の書き換え | 秘密情報や個人情報が、見るべきでない相手に見える状態になる |
| お金 | 無料枠や上限を決めた範囲での利用 | 課金が発生するリソースの作成、有料 API の大量呼び出し、購入 |
