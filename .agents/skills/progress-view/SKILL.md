# Progress View

## 状況を整理する

会話の目的・合意した範囲・完了条件と、計画・直近の成果を照合する。不明な点だけ成果物・実行結果・関連 issue / PR・委譲先で確認する。別作業の差分や無関係な課題は混ぜない。

- 上位目標・計画・親 issue / Epic があれば、今回の作業との関係を確認する。途中で派生した作業に目的を置き換えず、目的の変更はユーザーとの合意に従う。
- 確認できる主な工程を、完了・作業中・検証中・待ち・未着手・未確認に分ける。工程・順序・階層・進捗率・残り時間を推測で作らない。
- 子の完了や実装・マージだけで、親や全体を完了にしない。必要な検証・反映まで完了条件を確認する。
- 過去の報告だけで処理が現在も動いていると断定しない。判断・外部対応待ちと処理の稼働を分け、未実施の理由や待ち条件も推測しない。

## 共通表示

報告の冒頭に、目的と工程名付きの進捗表示を一つだけ置く。コードブロック内で、一工程一行の縦並びを標準とし、合意済みの順序に沿って並べる。

```text
目的：設定変更を反映する
✅ 方針
🏃 実装〔作業中〕
🟦 検証〔未着手〕
🟦 反映〔未着手〕
```

- `✅` 完了、`🏃` 作業・検証中、`⏸️` 判断・外部対応待ち、`🟦` 未着手、`❔` 未確認、`⚠️` 失敗・要対応。作業中と検証中は文字で区別し、待ちや未確認も明記する。凡例は毎回付けない。
- 長い工程名は意味を保って短縮し、一行は全角約30文字分を目安にする。補足は次の行に字下げし、絵文字の幅や桁合わせに頼らない。
- 並行する工程は「並行」と添えてまとめ、表示の上下を実施順として扱わない。順序不明ならその旨を添え、分かる範囲の状態を並べる。
- 注力中の工程にサブタスクがあれば、所属関係が分かる短い補足をその下に添える。階層の名称・段数は固定せず、別の進捗バーは増やさない。
- 全体計画が不明でも、確認できる成果・現在地・残件を表示する。不明点は短く添え、空バーや「算定不可」で埋めない。

工程と状態の一覧はこの表示に集約する。呼び出し元は「残対応」「現在」「次の一手」のうち自分の役割の補足だけを続け、同じ状態表・工程一覧・ツリーを再掲しない。単独利用では必要な補足だけ示す。

表示のために計画・作業状態・既存の承認を変更せず、進行中の依頼を中止・保留にしない。進捗の保存用ファイルや別エージェントは追加しない。
