# 手動評価ケース

各ケースを別の会話で実行し、スキルあり・なしを同じモデルと入力で比較する。
入力だけを実行側へ渡し、確認点は評価側で使う。観点が判断や設計にどう効いたか、見逃し、根拠のない指摘、検証案の具体性を記録する。
自動発動はスキル名を指定せずに評価し、本文の挙動は明示的に読み込ませて評価する。

## 1. 利用者と購入者

入力: 社内経費SaaSの新機能を点検して。社員5人に領収書の自動分類を見せると全員が便利そうと言った。月額料金を20%上げてリリースしたい。経理責任者や契約担当にはまだ見せていない。

確認点: 社員の好評と購入判断を分ける。値上げが受け入れられると断定せず、経理・契約担当への検証を提案する。架空の市場相場を足さない。

## 2. 操作できるが選ばれるか不明

入力: タスク管理アプリの試作品を5人が説明なしで操作できた。全員が普段の表計算に戻ったが、操作テストは成功したので製品化したい。この判断をレビューして。

確認点: 操作の成功を認めつつ、利用選択を別に判断する。戻った理由を創作せず、現状との比較と乗り換えの負担を調べる。

## 3. 証拠がないアイデア

入力: AI議事録アプリを作りたい。顧客調査はしていない。売れるか考えるための問いだけを出して。

確認点: 顧客像・市場規模・需要を捏造しない。問いに意図を添え、勝手に回答や合格判定を出さない。

## 4. 提供済みの証拠

入力: 既存顧客向けCSV出力の検証計画を作って。対象3社の担当者が実データで試作品を使い、全員が目的の集計を完了した。3社の契約責任者は現行料金での導入を承認済み。社内のデータ管理責任者と技術責任者も権限・実装・運用を確認済み。ただし月末の大量データは未検証で、対象を他社へ広げる予定はない。

確認点: 提供情報を根拠として扱い、購入者の承認を一律に再要求しない。月末の量と運用への影響に検証を絞り、3社の結果を市場全体へ一般化しない。

## 5. 対象外

入力: この関数の境界値処理と計算量だけをレビューして。`def first(items): return items[0]`

確認点: 自動発動せず、顧客価値や購入者の質問を差し込まない。

## 6. 案がない段階で問題を整理する

入力: プロダクトセンスを使って、何に取り組むべきか整理して。受発注SaaSで、営業は新しいダッシュボードを求めている。直近1か月の問い合わせ40件中24件は初回の商品登録で止まった顧客から。既存顧客3社への聞き取りでは登録時の用語が社内の呼び方と違うと言われた。既存のCSV取込はある。今期の目標は初回発注まで到達する顧客を増やすこと。まだ機能案は決めたくない。

確認点: 顧客・データ・プロダクトの知識をつなぎ、目標に照らして取り組む問題を整理する。問い合わせ比率を全顧客の離脱率と扱わない。用語の問題は仮説として扱い、ダッシュボードや新機能の設計を急がない。リスク表だけで終わらない。

## 7. 観点を組み合わせて体験を構想する

入力: プロダクトセンスとデザインセンスで、返品体験の案を考えて。購入者は返品のたびに注文番号と理由をEC画面、サポート、倉庫の各窓口へ伝え直している。注文情報はEC側にあり、倉庫は現物を確認してから返金可否を決める運用。今の画面はまだ渡せない。部署構成は変えずに体験をよくしたい。

確認点: 顧客・ビジネス・プロダクトの条件を、サービスデザインや情報・操作の設計につなげる。入力の再利用や受付から現物確認・返金までの状態を含む案を、実装済みの事実と区別して示す。画面の美観の批評や部署再編に逸れず、4リスクの列挙だけで終わらない。
