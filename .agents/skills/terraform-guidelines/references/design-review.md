# 構成設計とレビュー

## 根拠を集める

[practices.md](practices.md) の早見表から今回の論点の行を読み、リンク先の該当節を確認する。state や移行を扱うときは追加参照の節も読む。state 保存先の初回構築は [state-bootstrap.md](state-bootstrap.md) の 2 段階方式を前提にする。

既存構成のレビューでは、repo とコミットを固定して次の項目を追う。新規設計では同じ項目を要件・制約から「決めること」として扱い、存在しない AS-IS を創作しない。

- 実行ディレクトリ、root、backend、state、環境設定、provider と alias
- module の入出力と利用先 resource。権限 (IAM 等)、ログ、イベントやトリガーの接続を含む依存関係
- root に残る resource、child の責務、共有 locals・data source、保護設定 (削除保護・lifecycle 等)
- CI/CD・生成スクリプト・テスト・外部ツールが参照するパス、output、resource address

ディレクトリが child module・別 root・tfvars 置き場のどれなのかは、中身で区別する。

## 境界を決める

次の三つの境界を別々に判断する。

| 境界 | 判断すること |
|---|---|
| 環境・アカウント | 隔離、認証情報、環境差、環境追加時の再利用 |
| root・state | 独立した plan/apply、ライフサイクル、変更影響、復旧、権限、state 間依存で増える運用コスト |
| child module | 一機能としての責務、同時に変更する resource、公開する入出力、再利用先 |

出発点は、環境ディレクトリ別の薄い root と共通 child module の組み合わせ (Future の環境分離に基づく)。root が module を直接組み合わせ、output を別 module の input に渡す浅い構成を優先する。既存方式や要件の都合で別案のほうが適する場合は、出発点との比較とその案を選ぶ理由を示す。

- 環境分岐は child に散らさない。root で構成を選び、容量・保持期間などの値を child に渡す。依存先が作成済みか新規かの違いも呼び出し側で吸収し、child に取得・作成の分岐を持たせない
- provider 設定と backend は root に置く。child は provider 要件を宣言し、alias は明示的に受け取る
- 機能本体とその権限・ログ・イベント接続は同じ child にまとめ、policy の所有先を一意にする。機能横断の接続だけ root に残す
- 循環を避ける目的で ID や名前を文字列で組み立てない。参照を切ると依存グラフが失われ、作成・削除の順序が保証されなくなる。実際の参照関係と output を介した依存を確認し、module 間の相互参照だけで循環と断定しない
- 現状で機能している既存 module は維持する。単一 resource のラッパー、万能 module、設定を丸ごと渡すだけの module は避ける。module 数の上限は設けない
- module の分割と state の分割は別の判断。state を分けるなら、依存値の取得方法と構築・更新・復旧の順序も設計する

環境数、state 数、module の切り方、repo 分割、実行基盤は、今回の要件から導く。過去案件や参照資料での個別判断を共通ルールにしない。「拡張性」が環境・リージョン追加の容易さを指すのか、実行時の処理性能を指すのかも区別する。

## 成果物にまとめる

成果物は、依頼された保存先・形式で、読者が比較できる形にする。指定がなければ応答本文に出す。同じ内容を複数の場所に保存しない。

- **AS-IS / TO-BE ディレクトリツリー**: root、child、設定置き場、state の対応を注記し、抜粋・仮称・未実装はその旨を明記する。新規設計では AS-IS を省く
- **維持・分割・統合の表** (新規設計では module 一覧): 責務、主な入出力、所有 resource、配置理由、重要な依存
- **リファレンス対応表**: 資料の該当節リンク / 尊重するプラクティス / 今回の反映 / 適用しない点と理由。プラクティスと設計判断の書き分けは [practices.md](practices.md) の「根拠と説明の書き方」に従う
- **移行・検証の境界**: 既存 state を維持した再配置か、新規構築か。未確定の事項、検証済みの範囲、残る実装

図は、求められた場合か関係が複雑な場合だけ付ける。担当や承認フローの整備を、module の責務・境界を決めることの代わりにしない。対象外と指定された周辺システム (CI/CD・実行基盤・デプロイツール) への影響は、後続事項として分ける。

## 検証の実施範囲を区別する

設計のみの依頼なら、コード参照と依存確認にとどめ、実行検証済みとは書かない。実装・検証も依頼されたら、対象環境と副作用を確認したうえで次を実施する。

- fmt と validate。module の振る舞いを検証する test (Terraform 1.6+)。provider をモックするなら mock_provider (1.7+)
- 各環境の plan が、正しい環境と認証設定では成功し、環境の取り違えや必須入力の不足では失敗すること
- 既存資産を保つ変更では、同等条件での plan 比較と、resource address が変わる場合の対応。moved、import、state 操作の手順は別途検討し、無条件に再作成しない
- provider の不足と依存の循環がないこと。権限・削除保護・暗号化・バックアップなど既存の保護設定が保持されること
- 呼び出し側が参照するパス・output・resource address が変更に追従していること。モックが成功しても、実アカウントの権限・接続性の証明にはしない

完了時は成果物、判断根拠、実施した検証、未確定・未検証の事項を報告する。
