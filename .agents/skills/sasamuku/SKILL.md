# sasamuku

## 進め方

1. 依頼を下の索引と照らし合わせ、該当するプレイブックを `playbooks/<name>.md` で開く。
2. todo リストを作り、プレイブックの手順をそのまま写す。todo リストはハーネスの計画ツールで作る (Codex は `update_plan`、Claude Code は `TodoWrite` など)。使えるツールが無ければ (読み込みが要るツールしか無いときも同じ)、返信の中にリストを書き、手順を終えるたびに更新する。
3. やらない手順も消さずに残し、`skip: <理由>` を付ける。
4. 手順を順に実行する。実装・反映の完了を報告する前に、[anything-else](../anything-else/SKILL.md) を読み、確認観点を使って今回の操作が残した支障を確かめる。残対応の実行範囲と承認条件は元の依頼と本スキルに従う。プレイブック末尾の「**返信:**」に沿って返し、未解消の支障があれば再開条件も添える。

該当するプレイブックが無いときは、その旨を一言書いてから通常どおり進める。

## 必ず守ること

- **分からないことがある**: どのプレイブックの途中でも、コードや履歴を読めば分かることは、ユーザーに聞く前に **investigation** プレイブックの手順で調べる。調べ終えたら、元のプレイブックの手順に戻る。ユーザーに聞くのは、調べても決まらない判断だけにする。
- **確認を取るか迷う**: **principle-two-way-door** スキルで、その決定が Two-way door か One-way door かを見分ける。Two-way door なら聞かずに進め、結果を報告する。One-way door なら止まり、確認を取る。

## 任せると言われたとき

「任せる」「merge まで持っていって」「寝るので進めておいて」「終わるまで止まらないで」のように、確認を待たずに完了まで進めることを求められたら、その依頼の間は次を守る。範囲を示す語 (merge まで、完了まで、全部) が無く、どこまで任されたか分からなければ、先にそこを聞く。

- この節は「必ず守ること」の確認の規則を上書きする。プレイブックと、そこから呼ぶスキルの中の「確認を取る」「見せて止まる」「返して止まる」は止まらず、自分で既定の案を決めて進める。既定の案は元に戻しやすい側、範囲の小さい側を選ぶ。決めたことと、ほかにあった選択肢、外れたときの影響を、作業記録 (プレイブックが記録先を決めていればそこ) と返信に書く。プレイブックの末尾で止まるところは、残りを受け持つプレイブック (issue-planning の後は orchestrate。Issue が 1 つでも同じ) に渡し、返信は最後のプレイブックの形にする。
- それでも止まるのは、次だけにする。共有ブランチへの force-push、本番への反映 (戻せる構成でも止まる。main への merge で本番に反映される構成では merge の前)、作り直せないデータの削除、管理者相当などの強い権限付与、公開しているインターフェースを広げる・壊す変更、秘密情報の露出、チャットやメールでの外部への送信、大幅なコスト増加、実験では決まらない製品や好みの判断 (上の箇条のとおり既定案で通す確認の箇所と、プレイブックが既定案で進めると書いている箇所は除く)、本当の行き止まり。Issue や PR へのコメント (principle-two-way-door では One-way door) と merge は、任された作業の本体なので止まらない。本番に反映される構成かは、main への push で動く deploy の workflow、ホスティングの Git 連携の設定、README のデプロイの記述で判定する。どれかにデプロイの記述があるのに本番に届くかが読み取れなければ、分からないとして止まる側にする。どれにも記述が無ければ、反映されない構成とみなす。principle-two-way-door の One-way door のうち、この列挙に無いもの (依存のメジャー更新、基盤として使うライブラリの採用) は、その PR を merge の前で止めて確認待ちにし、ほかの作業は続ける。
- 課金や権限追加という理由だけでは確認で止めない。依頼への必要性、費用の見込額・利用規模・継続期間、権限の対象・操作・有効期間・取り消しやすさで判断する。小規模な費用や、対象と用途を絞った必要最小限の権限追加は、根拠と影響を作業記録に残して進める。管理者相当の権限や広い範囲への恒久的なアクセスは確認する。明示された予算上限と、必須のレビュー・承認・セキュリティ境界は守る。
- **issue-maintenance は例外。** 同プレイブックの具体案への承認を得てから更新する。
- 依頼者が名指しで「ここは聞いて」と言った箇所は、任せると言われても聞く。答えが来るまでは、その箇所に依存しない作業を進める。プレイブックが仮定で進めると書いていても、名指しの箇所は答えを待つ。

## 原則

次の原則のスキルを開いて読み、判断の拠り所にする。

- **principle-two-way-door**: 常に読む。決定が、元に戻せる Two-way door か、戻せない One-way door かを見分ける。
- **principle-documentation**: ドキュメント、指示ファイル、コードコメントを書くときと、見直すときに読む。
- **principle-aws-architecture**: AWS の構成を設計、レビューするときに読む。
- **principle-terraform**: Terraform の構成を設計、レビュー、変更するときに読む。
- **principle-coding**: コードやテストを書くとき、レビューするときに読む。
- **principle-design-system**: デザインシステム、トークン、`DESIGN.md` を作るとき、直すとき、UI をレビューするときに読む。
- **principle-design-harness**: エージェントに UI を作らせるとき、その足場を整えるときに読む。

## プレイブック

- **investigation**: コードを変えずに答えを出す依頼に使う。対象は、仕組み (X はどう動くか)、理由 (なぜこうなっているか)、正しさ (本当に合っているか)、選択 (どちらにするべきか)、失敗の原因 (なぜ CI が落ちたか)。依頼の例は「〜を調べて」「これ確認して」「解説して」「なにこれ」「どう思う？」。
- **autonomous-run**: 長いタスクを、終了条件を満たすまで止まらずに進める依頼に使う。対象は、席を外す間に任せる作業や、確かめられる完了条件まで繰り返す作業。依頼の例は「終わるまで回して」「テストが通るまで続けて」「もう寝るので進めておいて」。
- **orchestrate**: Epic や目的を渡されて、配下の Issue を PR にし、merge まで運ぶ依頼に使う。対象は、日をまたぐ作業や、担当を複数並べる作業で、自分はコードを書かずに指揮に回る。依頼の例は「この Epic を最後までやって」「Sub Issue を全部 merge まで持っていって」「この移行を任せる」。
- **session-pickup**: 前のセッションや別のエージェントの作業を引き継ぐ依頼に使う。対象は、途中で止まった作業記録、push 済みのブランチや PR、会話の記録からの再開。依頼の例は「続きをやって」「前回の続きから」「この PR を引き継いで」「どこまで進んだか見て続けて」。
- **issue-planning**: 目的を、着手できる Issue に落とす依頼に使う。対象は、1 つの Issue で済む作業から、Epic と Sub Issue に分ける大きな目標まで。依頼の例は「Issue にして」「Issue に分けて」「これを Epic にして」。システムの構成や移行方針を決める計画は architecture。
- **issue-maintenance**: 既存 Issue 群を実態に合わせて更新・再編する依頼に使う（「Issue を整理して」「構造を見直して」「引き継げる状態にして」）。新たな目的の計画は issue-planning。
- **feature**: 新しい機能や振る舞いを足す依頼に使う。対象は、仕様の決まった機能の追加から、設計を決めるところから始める変更まで。依頼の例は「〜を実装して」「〜できるようにして」「この Issue をやって」「機能を足して」。
- **architecture**: アプリケーション全体や複数の機能・システムをまたぐ構成、責務、データの所有者、移行方針を設計する依頼に使う。案を比べ、判断理由と実現する順序を設計書 1 つにまとめる。依頼の例は「新しいアプリの構成を考えて」「この基盤の移行を計画して」「アーキテクチャを設計して」。機能内で完結する実装は feature、Issue 化は issue-planning。
- **design-harness**: エージェントが UI を作っても品質がぶれない足場を、製品に入れる依頼に使う。対象は、デザインの基本原則を決めて最初の `DESIGN.md` を書き、部品の体系の足場を入れて、画面の 1 か所を作り直すところまで。その先 (画面全体の載せ替え、機械の検査、Storybook) の手順はまだ無い。依頼の例は「デザインハーネスを入れて」「DESIGN.md を作って」「デザインの基本原則を決めたい」「AI が作る画面がばらつくので仕組みを入れたい」。
- **eval**: スキル、プロンプト、指示ファイルの変更が、エージェントの振る舞いを良くするかを比べて確かめる依頼に使う。対象は、スキルのあり / なしの比較から、変更前と変更後の比較まで。依頼の例は「このスキルで良くなるか検証して」「A/B して」「効果があるか確かめて」。
