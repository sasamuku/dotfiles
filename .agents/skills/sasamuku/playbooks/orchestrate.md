# Orchestrate

**進行に責任を持つ。コードは書かず、誰に何を任せるかを決め、返ってきたものを確かめる。** 対象は、Epic (無ければ目的) を渡されて、配下の Issue を 1 つずつ PR にし、merge まで運ぶ依頼。Issue が 1 つでも merge まで任されていれば同じ手順で運ぶ。1 つのタスクを終了条件まで回すなら **autonomous-run**、PR を作るところまでなら **feature** に回す。merge まで運ぶ依頼なので、この手順に入った時点で SKILL.md の「任せると言われたとき」を当てる。

記録は autonomous-run の手順 5 に従い、Epic に作業記録の一覧、Issue ごとに作業記録を置く (autonomous-run 手順 1 の「Issue を作らない」より、こちらを優先する)。Epic が無く Issue が 1 つなら、一覧は置かず Issue の作業記録だけにし、以下の Epic の番号は Issue の番号に読み替える。起きる仕組みは `/loop` の 10 分間隔だけにし、見張り役は置かない。ループは手順 3 で最初の担当を起動した直後に始め、プロンプトにはこのプレイブックのパスと Epic の番号と「手順 4 の次の担当の起動と、手順 5〜7 を回す (Epic の一覧に、最初の 1 件の merge か、本番に反映される構成で merge の前に止めたことが記録されるまでは、次の担当を起動しない)」を書く。起きるたびに、open な PR すべての `gh pr view`、`gh pr checks`、`gh api repos/<owner>/<repo>/pulls/<n>/comments` を取り、PR の無い担当については届いている報告を見て、作業記録を更新する。止まる条件に当たった Issue はその Issue だけ止めて残りを続ける。全 Sub Issue が merge されるか外されるか止まったら、`/loop` を止める。

Codex で動かすときは、担当の起動、指示、終了を delegate-worker (`~/.agents/skills/delegate-worker/SKILL.md`) の「起動・追随 (Codex)」で読み替える (TaskStop も `interrupt_agent` にする)。`/loop` の 10 分間隔は `wait_agent` を 10 分の `timeout_ms` で呼ぶ繰り返しにし、general-purpose のサブエージェントは組み込みの `default` にする。

1. 単位を確かめる。Epic の Sub Issue を読み、各 Issue に「完了したと分かる証拠」(コマンドと期待する出力、画面、成果物) を書けるか確かめる。書けない Issue は、確かめられる部分 (送る JSON の形、テスト) を証拠として Issue に書き足し、人の目でしか確かめられない部分は「利用者の確認待ち」として、確かめてほしいことと確かめ方 (見る場所、操作、期待する状態) を Issue に書く。見た目などの好みは既定案で決めて進め、確認待ちに含める。確かめられる部分が 1 つも無い Issue も、同じように merge まで進める。確認待ちのある Issue は PR で close せず、merge 後も open のまま残す。Sub Issue が無い Epic は issue-planning で分け (確認は取らず既定案で進める)、戻る。着手の順序と依存は Issue の記述に従い、依存先が merge されるまで着手しない。依存先の merge が止まっても、依存先のブランチの上に積んで進めることはしない。記述に依存が無くても、同じファイルを触る Issue どうしは並列にせず、後続の多い方を先にして、先の merge を待つ。
2. Epic に作業記録の一覧を置く。すでに一覧があれば、**session-pickup** の手順 1〜4 で状態を組み立て、手順 4 以降をこの一覧から続ける。
3. 最初の 1 件を merge まで通す。その前に 1 度、main への merge で本番に反映される構成か (deploy の workflow や設定の有無) を確かめ、反映されるなら、どの PR も merge の前で止め、PR 作成と検証までは全 Issue で進める (依存先の merge を待つ Issue は待つ)。手順 4〜6 を 1 つの Issue で最後まで通し、指示の欠けを直してから残りを並べる。似た単位が安く並んでいても、最初の 1 件がその試験になる。
4. Issue ごとに担当を 1 人起動する。起動の前に自分の checkout で main を最新にする (`git pull --ff-only`。これはコードを書くことに当たらない)。**delegate-worker** スキルで worktree-worker を新しく起動し、その Issue だけを担当させる。渡すのは、Issue の URL、ゴールと完了の証拠、書いてよいパス (Issue の手がかりと自分で読んだコードから決め、並行する担当と重ねない) と書いてはいけないパス、してはいけない操作 (pass が出るまで merge しない、force-push しない、確認待ちのある Issue は PR 本文で `Closes` でなく `Refs` にする)、依存する Issue (同じファイルの理由で待った Issue も含む) の merge 時点の PR の差分と最後の報告。Phase D までの事前承認を付け、PR を作って CI の最初の結果を報告するところまで持たせ、そのあとも終了せずに次の指示を待たせる (CI が赤でも、直すのは手順 5 で頼まれてから)。delegate-worker と worktree-worker の「PR が届いたら終了させる」「担当の worktree に移動する」「Issue を close する PR にする」「worktree とブランチを削除しない」より、この手順を優先する。担当はそのブランチの唯一の書き手で、main の取り込み (rebase でなく merge)、push、修正はすべて担当にやらせる。自分は担当のブランチに触らない。同時に走らせるのは 10 人までとし、1 人終わるたびに次を起動する。
5. CI とレビューを通す。起きるたびに PR の生の状態を取り、CI の失敗とレビューコメントがあれば、担当に **babysit** `--auto --once` を頼む。コンフリクトがあれば、担当に main を取り込んで解かせる。review-pr の指摘 (手順 6) は投稿せず、SendMessage で担当に直接渡し、担当が直してコミットと push をする。
6. 作者でない検証役を通してから merge する。PR の必須チェックがすべて通り、コンフリクトが無くなったら、自分が **review-pr** スキルを実行し、加えて general-purpose のサブエージェント 1 人に、PR の head SHA を `git archive` で一時ディレクトリに展開させ、Issue の完了の証拠を実物で確かめさせる (テストを走らせる、画面を動かす。ファイルは変えず、外部への送信もしない)。review-pr の結果と検証役の報告を合わせて、自分が pass か差し戻しかを決める。CI が緑なことは判定の材料で、判定ではない。判定は head SHA 1 つに対して出し、push や main の取り込みで head が変われば取り直す。merge を止めるのは、利用者が踏む不具合、落ちた検証、間違った文書だけで、それ以外は follow-up として記録に残す。直しは同じ担当に差し戻す。pass が出た head を、担当に `gh pr merge` で main へ merge させる (方式はリポジトリの慣習。`--delete-branch` は付けない)。merge を確かめたら、リモートのブランチ削除と担当の終了 (shutdown_request) を自分が行い、ローカルの worktree は担当が終了してから片付ける。merge されたら、依存していた Issue の担当を起動する。
7. 監督する。担当の状態は、PR 前は worktree 内のファイル (`.git` を除く) の最新の更新時刻と届いた報告、PR 後はコミット、push、PR の動きで判断し、報告の文面だけで判断しない。PR 前の担当は 30 分、PR 後の担当は指示を渡してから起きる間隔 1 回分、動きが無ければ止まったとみなす (指示を渡していない待機中の担当と、CI が pending の間は数えない)。エラーで止まった、同じ修正を 3 回繰り返した担当も同じ。止まった担当は shutdown_request で終了させ、応じなければ TaskStop で止めてから替える。交代の担当は general-purpose のサブエージェントを isolation なしで起動し、前の担当の worktree のパスと、worktree-worker と同じ規則 (ブランチを変えない、コマンドは `git -C <worktree>` と絶対パスで打つ、コミットと push と PR の更新は承認済み、報告したら終了せず次の指示を待つ、babysit を含むすべてのコマンドの先頭に `cd <worktree> &&` を付ける) を指示に書いて、同じブランチの続きをさせる。前の担当の worktree は交代が終わるまで消さない。替え方は原因で分ける。文脈が尽きたなら範囲を小さく、接続が切れたなら同じ指示、道具のエラーなら別のモデル (opus なら sonnet、sonnet なら opus) にする。2 回替えても進まない Issue はそれに依存する Issue とともに外し、理由を記録に書く。起動した担当は全員、終了か交代のどちらかで終える。
8. main の取り込み、再試行、CI の flaky、レビューの振り分け、「続けてよいか」は利用者に聞かない。聞くのは SKILL.md の「任せると言われたとき」で止まる箇所だけにする。

**返信:** 最初に、元の目的の達成状況と残対応を示す。前提作業の成果はその後に置く。確認待ちの Issue ごとに、確かめてほしいこと、確かめ方、Issue と PR のリンクを示す。続けて、各 PR の状態と判定 (リンク)、外した Issue と理由、自分で決めたことと選択肢、記録先を示す。
