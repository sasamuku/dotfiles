# Issue planning

**計画に責任を持つ。コードは書かない。** 目的の認識を合わせ、着手できる単位の Issue に落とす。成果物は Issue である。

1. 目的を、完了したかを確かめられる形で 1〜2 文に書く。
2. 現状を調べる。関係するコード、既存の Issue と PR を読み、同じ目的の Issue がすでに無いかも確かめる。範囲が広いときは、観点ごとにサブエージェントへ読ませ、要約だけを受け取る。
3. 大きなゴールの認識を合わせる。目的、完了条件、範囲外にするものと、規模の見立て (1 つの Issue で済むか、分割が要るか) をユーザーに見せ、確認を取る。分割が要るときは、下の構造図の初版も添える。
4. 1 つの Issue で済むときは、Issue の下書き (ゴール、完了条件、確かめ方、手がかり) を見せて確認を取り、**create-issue** スキルで作る。手順 6 へ進む。
5. 分割が要るときは、次の順に進める。
   - 手順 3 で確認を取った大きなゴールで、**create-issue** スキルにより Epic を作る。
   - 小さなゴールに分ける。1 つの小さなゴールは、単独で完了して着地できるものにする (目安は PR 1 本)。不確実性の大きいものと、土台や確かめる仕組みを先に並べる。順序に意味があるものは、どのゴールの後に着手できるかを書く。調べれば決まる論点は、その調査や試作自体を最初のゴールにする。
   - 小さなゴールの認識を合わせる。構造図を更新して示したうえで、Sub Issue の下書き (ゴール、完了条件、確かめ方、依存するゴール、手がかり) を着手の順に並べて見せ、確認を取る。
   - **create-issue** スキルで Sub Issue を着手の順に作り、Epic に紐づける。作り終えたら、Epic 本文に Sub Issue の一覧 (番号へのリンク、着手の順序、依存) と未決の判断を追記する。
6. 実装は始めない。Issue を返して止まる。着手はユーザーの指示を待つ。

**構造図:** 分割が要るときは、Epic を親にしたツリーを 1 か所に書く。各 Sub Issue に、着手の順序、先行するもの (依存なしか、どれの後か)、並行できるものを添える。Epic が既存 Issue の流用か新規作成かも明記する。GitHub 上では、親子を Sub-issue、先行を「Blocked by」(Issue dependencies) で表し、本文にも依存を書く、と一言添える。1 つの Issue で済むときは出さない。

```
#12 [Epic] 目標 (既存 Issue を流用)
 ├─ ① 調査        依存なし
 ├─ ② 土台        依存なし (① と並行可)
 └─ ③ 切替        ← ①, ②
```

確認を取った下書きは、create-issue で承認を得た本文として扱う。下書きは、着手する人がその Issue だけを読んで動けるように書く。曖昧なまま渡すと、質問できない着手者は黙って間違える。

**返信:** 作った Issue の URL (分割したときは Epic と Sub Issue の一覧、着手の順序、依存)、未決の判断。
