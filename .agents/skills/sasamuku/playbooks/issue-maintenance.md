# Issue maintenance

作業の進展で古くなった Issue 群を、目的達成まで見通せる構造に組み直す。引き継ぎにも使う。整理の依頼だけで製品実装・デプロイは始めない。

## 手順

1. **目的を定める。** 当初の計画と、その後の合意・追加要件・対象外を照合する。既存の階層を前提にせず、親を閉じたときに達成すべき成果を決める。
2. **関連 Issue を集める。** **read-issue** で親・配下・依存先、本文・コメント・PR の参照先を辿る。同じ目的・機能・成果の語でも検索し、未所属・別 Epic 配下・クローズ済みを含める。目的に関係する範囲で全ページを取得し、重複を除く。検索範囲・語・関連する理由・取得失敗を記録し、未取得を「該当なし」にしない。
3. **全件を平らに並べる。** 下の棚卸し表を作り、コード・PR・実行結果と照合する。実装・環境への反映・利用確認を分け、環境・バージョン・実行条件を記す。別環境や条件付きの成功を全体の成功とせず、未確認を未実装と決めつけない。成果が混在する Issue は作業単位に分け、元の Issue との対応を残す。まだ関係を更新しない。
4. **分類して再編する。** 各作業を「目的に必要／外部前提・関連／対象外／判断待ち」に分け、必要な作業を成果・責務でまとめる。各分類の完了条件を定めてから、親子・依存先と下表の操作を選ぶ。進捗と構造の問題を分け、既存の親や担当者だけで分類しない。独立した完了条件のない中間 Epic は作らない。必要な成果に管理先がなければ新規案を足し、別目的の前提作業は依存・関連として残す。新たな目的の計画には **issue-planning**、承認後の新規作成には **create-issue** を使う。
5. **具体案を見せる。** 棚卸し表、変更前後のツリー、依存関係、並行可能な作業を提示する。構造を変えない場合も現状図を示す。親には全体の順序・未決事項、子には範囲・完了証拠・残作業・完了条件を置く。タイトル・本文・チェック・状態の編集案、理由、完了条件の変更、未達条件の移管先、履歴の保存方法まで示す。大きい案は全体図と承認単位の詳細に分け、図だけで本文編集まで承認されたと扱わない。通常の整理上の選択は推奨案にまとめ、別途の質問は案を確定できない判断に絞る。
6. **承認を待つ。** 具体案への明示承認まで、作成・本文編集・コメント投稿・状態・親子・依存関係を変更しない。「任せる」でも省略せず、同じ承認済み案は再確認しない。一部承認ならその範囲だけ反映し、追加・変更案は再提示する。
7. **反映する。** 更新直前に再取得し、承認の前提が変わっていれば、影響する棚卸し・案だけを更新して再提示する。他者の編集と依頼外の担当者・ラベルを保持する。失われる合意・判断根拠を保存するが、保存済みの全文アーカイブは重複させない。本文・状態等と正式な Sub Issue・依存関係を更新する。
8. **読み戻す。** 承認案と本文・状態・チェック・親子・依存を照合する。棚卸しの全行に反映先か除外・保留理由があり、漏れ・重複・依存の循環・移管先の欠落がないことを確認する。親の完了が目的達成を表すか、次に着手できる作業が明確かも確認し、未反映・未確認は分けて報告する。

## 棚卸しと提案

一つの表を棚卸しから再編案まで更新して使う。範囲外の Issue は関係だけ記録し、変更が必要なら承認対象に含める。

| Issue／作業単位 | 現在の親・依存 | 目的との関係 | 成果・責務 | 実績・証拠／残作業 | 問題 | 操作・行き先／除外・保留理由 |
| --- | --- | --- | --- | --- | --- | --- |

ツリーは text または Mermaid で示す。既存 Issue は番号とリンク、新規案は仮名を使い、各項目に状態・操作を添える。依存は親子と分ける。

```text
変更前                    変更案
Epic A                    Epic A（維持）
 ├─ B: 実装と検証          ├─ B: 実装（Cを統合）
 └─ C: Bと重複             └─ 新規案 D: 検証（Bの後）
                          C: Bへ移管してクローズ
```

## 操作の選び方

| 操作 | 条件 |
| --- | --- |
| 本文・タイトル・チェック更新 | 成果の担当範囲は適切で、記載だけが古い |
| 紐づけ・親の変更 | 必要な作業が計画から漏れている、または所属が不適切 |
| 分割 | 独立して完了できる成果や異なる依存条件が混在 |
| 統合 | 同じ成果・完了条件を重複管理 |
| 新規作成 | 管理先がなく、既存 Issue に加えると責務が混ざる |
| 置き換え | 目的・責務の変更が大きく、書き換えると経緯と現在の作業が混ざる |
| クローズ | 完了の証拠か不要の判断根拠がある、または残作業を移管済み |

統合・置き換えは移管先を用意し、残作業を移管して相互参照してから旧 Issue を閉じる。完了・重複・不要・移管の理由を区別し、未実装を実装完了として閉じない。

**返信:** 承認前は手順5の具体案を示す。承認後は更新先へのリンク、変更前後の対応と理由、状態変更、次の着手候補、残る判断・履歴の保存先・未確認範囲を報告する。整理の完了と、実装・配信・利用確認の完了を区別する。
