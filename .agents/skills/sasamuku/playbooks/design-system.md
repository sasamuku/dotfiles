# Design System

**プロダクトの見た目と言葉の決まりを `DESIGN.md` にそろえ、本番のコードに取り込める形で渡す。** 対象は、資産 (`DESIGN.md` と、その中のトークン、用語表) を作る依頼、整理する依頼、既存プロダクトのばらばらな値・部品・言葉をまとめて直す依頼。画面や操作を決める依頼は **design**。本番のコードは変えず、取り込みは **feature** に渡す。

依頼者に聞く箇所で答えが得られないときと、調べられないことは、**design** の冒頭と同じに扱う。質問、仮の答え、外れたときの影響を記録に書いて進め、仮定として返信にまとめる。記録は `docs/design/assets.md` (既存の置き場所があればそちら) に、判断、仮定、棚卸し、対応表、資産、引き渡し、直す候補の節を書く。写すときは対応表の節を省く。スクリプトは `docs/design/` に置く。

1. 深さを決める。記録の冒頭に、今回の判断と決めないことを書く。深さは依頼の言葉から次のどちらかに決める。決まらなければ聞き、答えが得られなければ「写す」で進める。
   - 写す (「DESIGN.md を作って」「トークンを書き出して」): 今ある値と言葉をそのまま資産にする。直さない。手順 4 は skip する。
   - 直す (「統一して」「ばらばらなので整えて」「デザインシステムを入れて」): 値を体系に寄せ、観点 (**design** の「確かめる観点」) で落ちる値を直す。

   製品の印象から変える依頼 (リブランド、別の雰囲気にしたい) は、先に **design** の「一から起こす」で方向性を決める。
2. 棚卸しする。既存の `DESIGN.md`、本番のトークン、プロジェクトの文書、過去の記録の「資産の候補」を読む。次に、画面のコード (CSS、テンプレート、コンポーネント) から次を集め、記録に表で書く。集めるスクリプトのパスを記録に書く。
   - 値: 色、書体、文字サイズ、太さ、余白、角、影。値ごとに、出現数と使われ方 (主操作、本文、背景、枠など)。
   - 部品: 同じ役割で繰り返し出る UI (ボタン、入力欄、表、カードなど) と、役割ごとの見た目の種類の数。
   - 言葉: 同じものを指す違う言葉、同じ操作の違う名前、日付や数の書式のゆれ。
3. トークンと言葉を決める。
   - 写す: 色と文字は役割ごとに 1 つ拾う。余白と角は 4 px の倍数の値を拾い、全丸の角 (`999px` など) は `full` として拾う。観点で落ちる値も直さずに拾い、直す候補に挙げる。4 px の倍数でない余白と角は拾わず、直す候補に挙げる。
   - 直す: 棚卸しした値をすべて、寄せる先のトークンに対応させ、対応表 (今の値 / 出現数 / 寄せる先 / 見た目が変わるか) を記録に書く。色は役割ごとに 1 つ (中立色、アクセント 1 色、意味色)、文字サイズは固定の段階表、余白と角は 4 px の倍数の段階に寄せる。寄せる先は出現数の多い値を基本にし、観点で落ちる値は通る値に直す。部品は役割ごとに見た目を 1 つに寄せる。部品の見た目を先に決め、値ごとの寄せ先と食い違えば部品のほうを採る。言葉はプロジェクトの文書か依頼者の言葉にあるほうへ寄せる。どちらにも無ければ画面で多いほうへ寄せ、仮定として返す。色相や書体が変わる寄せ方は、対応表を依頼者に見せて決めてもらう。並べて見分けの付かない値をまとめるだけなら、見せずに進める。
4. 確かめる (直すとき)。既存の画面を写した使い捨ての試作に、対応表のトークンを当てる。幅 375 / 768 / 1440 で、横スクロール、コントラスト比、押せる要素の大きさ、入力欄の文字サイズ、Tab だけで操作できるかを取り、同じ幅で元の画面とスクリーンショットを並べる。状態の切り替えと壊す入力は要らない。観点で落ちる箇所は対応表を直して測り直す。値と部品の見た目を変えても直らない箇所 (配置や操作を変える必要があるもの) は、直す候補に書いて **design** に回す。見た目が変わった箇所を記録に書き、依頼者に見せる。試作はリポジトリの外に置き、コミットしない。
5. `DESIGN.md` に書く。下の「資産」の書式に従う。
   - 優先すること、ルール、使わない言い換えは、依頼者に確かめたものか、プロジェクトの文書にあるものだけを書き、無ければ空にする。指示ファイルに既にある規約は書かない。直すときに寄せた言葉は、寄せられた側を使わない言い換えに書く。
   - 値の使い道と用語の意味は、既存の画面と文書で見て取れる範囲を書き、何に使わないかは根拠が無ければ書かない。
   - 本番のコードにトークンがあるときは、値の変更を front matter に書かず、対応表のまま手順 6 で渡す (下の「トークン」)。
6. 渡す。本番への取り込みを、次の順で 1 つずつ **feature** への依頼文にし、記録の「引き渡し」に書く。写すときは 1 だけを渡し、直す候補を添える。依頼が本番への反映まで含むときは、この順に **feature** で進める。
   1. トークンを本番に置く (`npx @google/design.md export` か CSS 変数)。見た目は変えない。
   2. 直書きの値のうち、対応表で見た目が変わらないものをトークンに置き換える。受け入れ条件は、幅 375 / 768 / 1440 のスクリーンショットが前後で変わらないこと。
   3. 見た目が変わる箇所 (寄せた値、観点で直した値、言葉) を画面ごとに直す。受け入れ条件は手順 4 の計測。
   4. 役割が同じ部品をまとめ、トークン外の値を禁じる lint を足す。

**返信:**

- 深さと、資産に入れた差分
- 対応表の要約 (寄せた値の数、見た目が変わる箇所、依頼者が決めた点)
- 確かめた結果 (計測、スクリーンショットの比較。無ければ未確認と明記)
- **feature** に渡す依頼の順と、記録の場所
- 仮定の一覧、直す候補、未確認の項目

## 資産

設計を重ねるほど次の設計が速く確かになるように、プロジェクトに残すもの。**design** は手順 2 で読み、手順 7 で戻す。既存の置き場所と書式があればそちらを使い、同じものをもう 1 つ作らない。

- `DESIGN.md` (無ければリポジトリのルートに作る): 人とエージェントが最初に読むファイル。書式は [DESIGN.md の仕様](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) (Google Labs、alpha 版) に従い、下の骨組みから始める。仕様にある節は、見出しの名前と順序を変えない。書くことが無い節は見出しごと省く。仕様に無い節 (用語表、正本の場所) は末尾に置く。確かめていない欄は空にし、「未確認」で埋めない。front matter を除いて 150 行を超えたら、節を別ファイルに分けて参照を残す。
  - Overview: 誰が、どんな状況で、何のために使うか。この製品で何を優先するか (多くても 7 個)。
  - Colors から Components まで: トークンごとに、何に使い、何に使わないか。値は書かず `{colors.primary}` の形で参照する。Components は部品の見た目と状態の決まりで、props や実装は書かない。
  - Do's and Don'ts: この製品に固有の判断 (以下「ルール」)。1 件ごとに ID、強度 (必須は例外なし / 原則は理由があれば外れてよい / 任意は選んでよい)、「<条件> のとき <こうする>」、理由、出どころの記録を書く。禁止には代わりに使うものを添える。
  - 用語表: 利用者と依頼者の言葉と、使わない言い換え。
  - 正本の場所: トークン、部品、記録、計測スクリプト。食い違ったときにどれを正とするか。
- トークン: `DESIGN.md` の front matter に書く。名前は既存の型に揃え、無ければ仕様の推奨名 (`primary`、`on-surface`、`body-md`、`sm` / `md` / `lg` など) を使う。余白と角の段階は、値の小さい順に `xs` から名前を付ける。骨組みに無いキー (`components` など) は、仕様を開いて確かめたときだけ使う。本番のコードにトークンがあれば (CSS 変数や Tailwind の theme のように名前の付いた値。直書きの値は含めない)、そこから写し、本番を正とする。このときの値の追加と修正は、front matter と使い道の記述の更新も含めて **feature** に渡す。本番のコードにトークンが無ければ front matter を正とし、本番への取り込み (`npx @google/design.md export`) を **feature** に渡す。本番のコードは変えない。
- `DESIGN.md` を書いたら `npx @google/design.md lint DESIGN.md` を通し、error を直す。warning は記録に書く。実行できなければ未確認と書く。
- プロジェクトの指示ファイル (`AGENTS.md` / `CLAUDE.md`) に `DESIGN.md` への参照が無ければ、1 行足す。

````markdown
- R-001 (原則): 絞り込みの結果が 0 件のとき、空の表示の中に条件を解除する操作を置く。理由: 解除の方法が分からず止まった。出どころ: docs/design/<対象>.md

## 用語表

| 言葉 | 意味 | 使わない言い換え |
|---|---|---|

## 正本の場所

| もの | 場所 | 食い違ったときに正とするもの |
|---|---|---|
| トークン | <本番のコードの場所。無ければ「この front matter」> | <本番のコード / この front matter> |
| 部品 | | |
| 記録 | docs/design/ | |
| 計測スクリプト | | |
````

**入れないもの:** 一般的な良し悪し (**design** の「確かめる観点」で足りる)、コードを読めば分かる事実 (部品の props、実装の構成)、プロジェクトの指示ファイルに既にある規約、その画面だけの調整 (「この画面の余白を詰める」)。規則は多いほど読まれなくなる。これに当たるものは下の基準を見る前に外し、候補にも残さない。観点が求める結果をこの製品でどう満たしたか (狭い幅では表をリストに積み替える、など) は、一般的な良し悪しに当たらない。当たるか迷うものは候補に残す。

**入れる基準:** どれも先に、題材が変わっても当てはまる「<条件> のとき <こうする>」に書き直す。書き直せないものはその画面だけの調整なので、入れない。

- 依頼者が方針として述べたこと、確定した用語: 1 回で入れる。
- 計測、作者以外の目、依頼者の指摘から得た判断: 書き直せたものは、初回は候補に残す。過去の記録の「資産の候補」に同じ種類があれば入れる。
- トークン: 足りない値はまず既存の段階に寄せる。寄せられず、2 か所以上で使う値だけを足す。
- 今回の推奨が既存のルールや用語表に反した: 依頼者が今回決めたことを優先し、ルールを直すか、例外の条件を足すか、削る。実物と食い違う値と、使われなくなったルールも削る。

**振り分け先 (基準を満たしたもの):** 値はトークン、値の使い道は Colors から Components までの該当する節、言葉は用語表、判断はルール。機械で判定できるもの (トークン外の値、禁止した書き方) はルールに書いたうえで、lint やテストにする作業を **feature** に渡す。同じ独自の UI が 2 回出たら、部品にする作業を **feature** に渡す。
