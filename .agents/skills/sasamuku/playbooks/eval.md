# Eval

**実験の設計に責任を持つ。計画し、走らせ、まとめる。** スキル、プロンプト、指示ファイルの変更がエージェントの振る舞いを良くするかを、取り入れる前に確かめる。版ごとにサブエージェント (実行役) に同じ依頼をこなさせ、別のサブエージェント (採点役) に成果物を採点させる。

**隠すこと:** 実行役は、評価されていると気付くと、普段と違う動きをすることがある。

- 実行役が見るディレクトリ、ファイル、依頼文に、評価、テスト、採点、比較、実験などの語を入れない。ディレクトリやファイルの名前は、利用者が実際のプロジェクトに付けそうなものにする。
- 依頼文は、利用者が普通に打つ依頼にする。何を測っているかは書かない。
- どのスキルや原則を使ったかを、実行役に挙げさせない。従ったかは、手順 5 の記録と成果物の形で判断する。
- ほかの実行役がいることを伝えない。
- 読んでよいファイルの範囲を、すべての実行役で同じにする。ハーネスが自動で読み込む指示 (利用者全体の指示ファイルやスキル) も、この範囲に含めて確かめる。比べる版のほかに差を作らず、比べる版と重なる指示も入れない。外せずに版の差が崩れるなら、走らせずに、測れないと返す。この規則は実行役が読む範囲の話で、手順 1 の採点の根拠には当てない。
- 採点基準と、どの実行役にどの版を渡したかの控えは、実行役の作業用ディレクトリの外に置く。読まれていないかは、手順 5 で確かめる。
- 採点役には、どの成果物がどの版かを隠し、A、B のような名前で渡す。全員の成果物を、同じ基準でまとめて採点させる。

**手順:**

1. 比べる版 (スキルのあり / なし、変更前 / 変更後など) と、成功とみなす振る舞いを書く。採点基準を 3〜6 項目、結果を見る前に決める。基準は採点役にだけ渡す。
   採点基準と、仕込む欠陥や課題は、比べるスキルや指示の本文を読む前に書く。すでに読んでいるなら、本文を渡さないサブエージェントに書かせる。本文を読んだ者が項目を選ぶと、あり版 (変更後の版) が勝つことが最初から決まる。
   書き手は手順 2 で用意する「なし版 (変更前の版)」の作業用ディレクトリを先に作り、そこを起点に起動する。渡すのは、比べる目的、公式資料を参照してよいこと、実行役と同じ道具の範囲まで。目的は「Terraform 構成のレビュー」「回答の書き方」のように対象物と行為の 2 語程度で自分の言葉で書き、スキルの description、見出し、本文の語は流用しない。本文、差分、書き直した意図は渡さない。書き手には採点基準 (3〜6 項目、下の根拠の列つき) と、仕込む欠陥を入れた課題と、手順 3 の依頼文をまとめて書かせる。書き手の記録に本文のパスがあれば、別の書き手でやり直す。返ってきた基準に、自分は項目を足したり言い換えたりしない。下の条件に合わない項目を外すだけにする。
   採点項目ごとに「根拠」の列を付け、本文の外にある出典を書く。出典になるのは、公式資料の節、リポジトリにある既存の規則 (比べる本文そのものは、新旧とも含めない)、実行すると失敗する事実のどれか 1 つでよい。公式資料の節は固定する前に開いて、その内容があることを確かめる。実行結果を根拠にする項目は、書き手が実際に実行して失敗を確かめ、コマンドと結果を添える。実行できなければ別の出典に替えるか、外す。根拠が両版に共通して見えるものでもよく、差が出なければ、それも結果として書く。「隠すこと」の読む範囲の規則は実行役の入力の話で、根拠の判断とは別である。
   基準を固定する前に、根拠の列がすべて埋まっていることを確かめる。空の項目と、根拠が本文にしか無い項目は外す。外した後に 3 項目を下回るなら、書き直させずに、走らせずに、測れないと返す。6 項目を超えて返ってきたら、自分で選ばずに、書き手に 6 まで絞らせる。
2. 実行役ごとに作業用のディレクトリを用意し、比べる版を置く。普通の依頼なら手元にあるもの (プロジェクトの骨組み、自然に読むはずのスキル) も置く。
3. 依頼文を 1 つ用意し (手順 1 で書き手に書かせたときはそれを使う)、すべての実行役に同じ文を渡す。読み書きしてよいのは作業用のディレクトリだけだと、依頼文に書く。スキルが扱う場面が複数あるなら、場面ごとに依頼文を書き、依頼文ごとに手順 2〜6 を回す。
4. 実行役を、作業用のディレクトリを起点にして並列に起動する。起動の前に、実行役に読み込まれる指示とスキルの一覧を確かめる。版ごとに最低 1 人とし、結果がぶれそうなら人数を増やす。実行役に許す道具は版ごとに同じにし、検査 (fmt、lint、テスト) の実行まで比べたいなら Bash も許す。
   Claude Code で実行役を立てるときは、作業用のディレクトリを cwd にして `env -u CLAUDECODE claude -p "<依頼文>" --setting-sources project --allowedTools <道具> --output-format stream-json --verbose` を sandbox の外で走らせる。sandbox の中では保存済みのログインに届かない。`--setting-sources project` で利用者全体のスキルと指示を外す。起動の前に、同じ条件で「使える skill の名前を列挙して」と 1 回だけ投げ、比べる版以外のスキルが見えないことを確かめる。worktree に隔離したセッションでは、guard がリポジトリのコピーや入れ子の起動を拒むので、`ExitWorktree keep` で元の checkout に戻ってから組む。
5. 実行役が実際に読んだファイルを、ハーネスが残す実行の記録で確かめる。本人の報告は信じない。範囲の外を読んでいた実行は、捨ててやり直す。記録が読めないときは、確かめられなかったと書く。stream-json の記録なら、`assistant` 行の `tool_use` から Read のパスと Skill の名前を取り出す。
6. 全員の実行がそろってから、採点役を 1 人起動し、成果物と採点基準を渡す。
7. 成果物をすべて自分で最後まで読み、採点役の判定と比べる。食い違ったら、自分か採点役の偏りか、基準のあいまいさを疑う。採点基準に無い副作用 (コードの量、頼んでいない構成) も書く。

**返信:** 比べた版、採点基準、実行役ごとの所見、採点役の判定、自分のまとめ、残る限界 (人数、採点役の数、採点基準を自分で書いたこと)、その版を取り入れるかの推奨。
