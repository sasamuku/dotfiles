# Eval

**実験の設計に責任を持つ。計画し、走らせ、まとめる。** スキル、プロンプト、指示ファイルの変更がエージェントの振る舞いを良くするかを、取り入れる前に確かめる。版ごとにサブエージェント (実行役) に同じ依頼をこなさせ、別のサブエージェント (採点役) に成果物を採点させる。

**隠すこと:** 実行役は、評価されていると気付くと、普段と違う動きをすることがある。

- 実行役が見るディレクトリ、ファイル、依頼文に、評価、テスト、採点、比較、実験などの語を入れない。ディレクトリやファイルの名前は、利用者が実際のプロジェクトに付けそうなものにする。
- 依頼文は、利用者が普通に打つ依頼にする。何を測っているかは書かない。
- どのスキルや原則を使ったかを、実行役に挙げさせない。従ったかは、手順 5 の記録と成果物の形で判断する。
- ほかの実行役がいることを伝えない。
- 読んでよいファイルの範囲を、すべての実行役で同じにする。ハーネスが自動で読み込む指示 (利用者全体の指示ファイルやスキル) も、この範囲に含めて確かめる。比べる版のほかに差を作らず、比べる版と重なる指示も入れない。外せずに版の差が崩れるなら、走らせずに、測れないと返す。この規則は実行役が読む範囲の話で、手順 1 の採点の根拠には当てない。
- 採点基準と、どの実行役にどの版を渡したかの控えは、実行役の作業用ディレクトリの外に置く。読まれていないかは、手順 5 で確かめる。
- 採点役には、どの成果物がどの版かを隠し、A、B のような名前で渡す。全員の成果物を、同じ基準でまとめて採点させる。

**手順:**

1. 比べる版 (スキルのあり / なし、変更前 / 変更後など)、利用者が求める成果・判断、実行・校正・採点それぞれの回数と再試行の上限を決める。採点基準は結果を見る前に 3〜6 軸で作り、実行役には渡さない。
   採点基準と、仕込む欠陥や課題は、比べるスキルや指示の本文を読む前に書く。すでに読んでいるなら、本文を渡さないサブエージェントに書かせる。本文を読んだ者が項目を選ぶと、あり版 (変更後の版) が勝つことが最初から決まる。
   書き手は手順 2 の「なし版 (変更前の版)」の作業用ディレクトリを先に作り、そこを起点に起動する。対象と行為に加え、利用者の要件、求める成果・判断、公式資料の参照許可、実行役と同じ道具の範囲を渡す。スキルの description・見出し・本文の語、本文、差分、書き直した意図は渡さない。書き手には基準、仕込む欠陥を入れた課題、手順 3 の依頼文をまとめて書かせる。記録に本文の参照があれば、その案は使わない。自分で項目を足さず、修正は同じ独立性を保った書き手に返す。
   各軸では独立した条件を分け、それぞれの「充足 / 不足 / 未確認 / 対象外」の判定条件と根拠を付ける。複数の条件を一つの点数に束ねない。必要なら技術的な正しさと、比較・推奨など利用者の判断に役立つ質を別の軸にする。スキルの手順に従ったこと自体は加点しない。
   根拠は本文の外に置く。利用者の要件、公式資料の節、既存の規則 (比べる本文は新旧とも除く)、実行で確かめた事実を使う。公式資料は開いて内容を確かめ、実行を根拠にするならコマンドと結果を添える。未実行なら別の根拠に替えるか、その条件を外す。両版に共通する根拠でもよい。根拠が無い条件を外して 3 軸を下回るなら測れないと返し、6 軸を超えるなら書き手に絞らせる。
   実行前に、小さな合格・不合格・境界の例で採点役を校正する。期待する判定は先に教えず、実際の判定と比べてずれを調べる。曖昧な条件は書き手に直させ、変更理由を記録し、再確認して固定する。総合点は任意とし、出すなら重み、未確認・対象外の扱い、集計ルールを先に固定する。重大欠陥の判定条件も定め、他の得点で相殺しない。上限までに基準を固定できなければ、測れないと返す。
2. 実行役ごとに作業用のディレクトリを用意し、比べる版を置く。普通の依頼なら手元にあるもの (プロジェクトの骨組み、自然に読むはずのスキル) も置く。
3. 依頼文を 1 つ用意し (手順 1 で書き手に書かせたときはそれを使う)、すべての実行役に同じ文を渡す。読み書きしてよいのは作業用のディレクトリだけだと、依頼文に書く。スキルが扱う場面が複数あるなら、場面ごとに依頼文を書き、依頼文ごとに手順 2〜6 を回す。
4. 実行役を、作業用のディレクトリを起点にして並列に起動する。起動の前に、実行役に読み込まれる指示とスキルの一覧を確かめる。版ごとに最低 1 人とし、手順 1 で決めた実行数で走らせる。実行役に許す道具は版ごとに同じにし、検査 (fmt、lint、テスト) の実行まで比べたいなら Bash も許す。
   Claude Code で実行役を立てるときは、作業用のディレクトリを cwd にして `env -u CLAUDECODE claude -p "<依頼文>" --setting-sources project --allowedTools <道具> --output-format stream-json --verbose` を sandbox の外で走らせる。sandbox の中では保存済みのログインに届かない。[設定の読込元を指定するフラグ](https://code.claude.com/docs/en/cli-reference)だけで全指示を外せたとは扱わない。同じ条件で事前起動し、スキル一覧と指示の読込記録を確認する。比べる版以外の指示が残り、比較を崩すなら走らせない。worktree に隔離したセッションでは、guard がリポジトリのコピーや入れ子の起動を拒むので、`ExitWorktree keep` で元の checkout に戻ってから組む。
5. 実行役が実際に読んだファイルを、ハーネスが残す実行の記録で確かめる。本人の報告は信じない。範囲の外を読んでいた実行は無効として記録し、事前に決めた上限内でだけやり直す。記録が読めないときは、確かめられなかったと書く。stream-json の記録なら、`assistant` 行の `tool_use` から Read のパスと Skill の名前を取り出す。
6. 全員の実行がそろってから、新しい文脈の採点役に匿名の成果物と固定した基準を渡し、条件ごとの判定と成果物内の根拠を記録させる。同じ成果物・基準で匿名名と提示順を変え、別の新しい文脈の採点役にも既存の採点を見せずに判定させる。判定や根拠の解釈が割れた条件を列挙し、合意のない差は優劣不明とする。多数決や最後の点数で解決せず、同点だけで同等としない。
7. 成果物をすべて自分で最後まで読み、採点役の判定と比べる。食い違いは偏りや基準の曖昧さを調べ、改善効果、重大欠陥、採点の揺れ、基準外の副作用 (コードの量、頼んでいない構成など) を分ける。結果を見て基準を直した場合は旧基準・旧結果も保存し、全件を同じ新基準で再評価する。上限に達して再評価できなければ、その比較は未完了とする。

**返信:** 比べた版、固定した基準・集計ルール、実行数・無効と再試行の記録、条件ごとの判定と根拠、採点が割れた条件、改善効果・重大欠陥・採点の揺れ・基準外の副作用、採用の推奨を示す。限界には、標本数、採点役の数、同じモデルに共通する偏り、基準作成者の独立性、読込範囲を確認できなかった点、同じ課題に合わせて追加修正した場合の偏りを含める。少数例の差を一般的な効果とみなさない。
