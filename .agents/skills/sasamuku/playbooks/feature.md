# Feature

**設計に責任を持つ。計画し、レビューし、確かめる。** 実装はサブエージェントに任せ、自分は指揮に回る。

1. 変更する範囲のコードと実行の流れを読む。
2. 設計を決める。
   - Issue や Docs に設計が既にあれば、それを土台にする。この変更で変わる点だけを、元の構造を保って更新する。
   - 無ければ、ロジックを書く前に、扱うデータの形と、その組み立て方を決める。最初の案が十分に見えても、構造の違う案を最低 2 つ出し、トレードオフの表で比べてから 1 つを選ぶ。細部だけが違う案は、別の案に数えない。決めた設計は、下のテンプレートで記録する。
3. 作業を、確かめてからコミットできる単位に分け、順序を付けて todo リストに書く。土台や確かめる仕組みのように、先に終えなければならない作業を前に置く。別の worktree で並べて進める必要がある作業は、この変更に含めず、**create-issue** スキルで別の Issue に切り出す。
4. 単位ごとに、新しく起動した **ssmk-agent** サブエージェント 1 人に実装を任せ、自分と同じ worktree で作らせる。渡す範囲は具体的にする: 作業する worktree のパス、対象のファイル、手順 2 の設計 (記録があればその場所、無ければ設計の全文)、完了条件。この手順は、変更が小さくても skip しない。自分で書くと、レビューが自分の書いたものの追認になる。
5. 返ってきた差分を自分で読んでレビューする。サブエージェントの報告をそのまま信じない。直させるときは同じエージェントを使い回さず、元の指示、直す点、前の報告をまとめて、新しい ssmk-agent に渡す。設計を変えたら、手順 2 の記録も更新する。
6. 変更が効く場所で確かめる (UI なら画面、API なら実際のリクエスト)。確かめられなかったとき、別の場所でしか確かめていないときは、通ったことにせず、そう書く。
7. 確かめた単位を **commit** スキルでコミットし、残りの単位があれば手順 4 に戻る。
8. **create-pr** スキルで PR を作る。

**設計の記録のテンプレート:** 記録先は、上から順に最初に当てはまるものにする。

1. 設計が Issue や Docs に既にある: その文書を更新する。テンプレートは使わない。
2. Issue がある: 「設計: <機能>」コメントを 1 つだけ作り、以後はそのコメントを更新する。
3. PR を作る: 手順 8 で PR の本文に書く。
4. どれにも当てはまらない: 設計を入れたコミットのメッセージ本文に書く。折りたたみは使わない。

```markdown
## 設計: <機能>

**データの形:** <型や構造>

**選んだ案と理由:** <案> — <理由>

<details>
<summary>比べた案</summary>

| 案 | 長所 | 短所 |
|---|---|---|

</details>

**判断の記録**

| 日付 | 判断 | 理由 |
|---|---|---|

**未決の判断:** <無ければ「なし」>
```

**返信:** 作ったもの、選んだ設計とその理由 (案を比べたときは表) と記録の場所、作業の分け方、確かめた方法と結果、PR の URL、未決の判断。
