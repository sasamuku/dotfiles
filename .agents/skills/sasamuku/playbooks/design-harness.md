# Design Harness

**エージェントが UI を作っても品質がぶれないように、基本原則と `DESIGN.md` から足場を育てる。** 対象は、作るものは決まっているが、見た目は AI が一度に出したままの製品。判断は **principle-design-system** と **principle-design-harness** スキルに拠る。

扱うのは、基本原則を決めて最初の `DESIGN.md` を書き、部品の体系の足場を入れて、画面を 1 か所ずつ作り直し、製品の規模に合う検査を選んで足すところまで。

依頼者に聞く箇所は 1 問ずつ聞く。記録は `docs/design-system/harness.md` (既存の置き場所があればそちら) に書く。

1. 依頼者と製品の関係を確かめる。自分たちの製品か、頼まれて作っているか、誰が決められるか。文書から読み取れなければ聞く。文書の中の呼び方を、その関係に合わせる。
2. 現状を調べる。読み取りだけで行う。
   - 構成 (フレームワーク、スタイルの書き方) と、部品の数と種類 (ボタン、入力欄、ダイアログなど)。
   - 名前の付いた値 (CSS 変数など) の数と、直書きの色、文字サイズ、角の種類の数。
   - `DESIGN.md`、Storybook、指示ファイル、デザインの検査があるか。既にある検査 (lint、型、テスト、CI) は何か。
   - テストが見た目の実装 (クラス名など) にどれだけ頼っているか。
   - 規模。画面の数、部品の数、変更を入れる人とエージェントの数。手順 17 で入れるものを選ぶ材料にする。
   - 今の画面を、見た目が変わる状態 (画面幅、開閉、選択中など) ごとに撮る。ブラウザは画面に出さずに (ヘッドレスで) 動かす。
3. 部品に使う体系を決める。今の書き方のまま進めるか、エージェントが既に知っている体系 (shadcn/ui など) に載せ替えるか、見た目を持たない部品のライブラリから振る舞いだけを借りるか。製品にとって戻しにくい決定なので、次の材料を添えて依頼者に聞く。
   - 見た目を作り直すなら、スタイルの大半はどのみち書き換える。載せ替えの費用はその分小さい。
   - 自作が難しい部品 (ダイアログ、メニュー、コンボボックス) が今あるか、この先要るか。
   - 載せ替えで直すことになるテストの量。
4. 過去の判断を集める。Issue、PR、設計書、仕様書、決定の記録、コミットの履歴、画面の文言のうち、あるものから、何かを選び何かを捨てた判断を、理由と出どころを付けて拾う。集め終わるまで、基本原則の案は作らない。集めた判断を、一度も変わらなかったものと、何度も変わったものに分ける。前者が基本原則の候補で、後者は今の方向として別に扱う。
5. 書かれた意図と今の画面を突き合わせ、食い違いを書き出す。
6. 基本原則の案を出す。
   - 形は短い言葉に「すること」と「しないこと」を 1 文ずつ添えたもので、3〜5 個にする。
   - 案は当てるためではなく、依頼者の言葉を引き出すために出す。違うと言われたら、言い換えを重ねず、手順 4 の根拠に戻る。
   - 依頼者が自分の言葉を出したら、それを正とし、エージェントの言葉に置き換えない。整えるのは、重なりの境目と「すること」「しないこと」だけにする。
7. 案を確かめる。
   - 機能に依らないか。まだ無い機能や画面を 2〜3 個挙げ、そこにも当てはまるかを見る。画面の名前、寸法、部品の名前が入っていたら、基本原則から外し、下の「決定の行き先」で置き場所を決める。依頼者の言葉は消さない。
   - 重ならないか。具体的な場面を原則の数だけ挙げ、場面ごとに効く原則が 1 つに決まるかを見る。場面は、判断が 1 つで済む粒度で挙げる。同じ場面で同じ答えを出す 2 つは、1 つにまとめる。
   - 依頼者の言葉どうしが食い違うときは、どちらかを消さず、「それは何から感じてほしいか」を選択肢で聞く。
8. 見た目の案で確かめる。実際の画面 1 つを題材に、基本原則は同じで解釈の違う案を 2〜3 個作る。
   - 使い捨ての HTML 1 つにまとめ、データは同じにする。製品のコードには入れない。長いページは、最初に見える範囲だけで作ってよい。
   - 文言を基本原則に合わせて直すときは、どの案でも同じにし、未確認として伝える。
   - スクリーンショットを自分で見て、崩れを直してから見せる。画面全体に加えて、繰り返し出る小さな要素 (一覧の行、ボタン、印など) の拡大も見せる。
   - 依頼者に選んでもらい、理由を聞く。理由が基本原則に無いことを言っていれば、基本原則に足す。
   - 決まったのは、選んだ理由として挙がった点だけである。案に含まれるほかの要素を書き出し、記録に「未確認」と書く。未確認の要素はルールにせず、最初の実物で見てもらう。
9. 選んだ案から、最初のトークンを決める。
   - 名前は手順 3 で決めた体系の名付け方に合わせる。
   - 寄せる先の製品やブランドがあるときは、先に、どのくらい寄せるかを聞く (そっくりにする、色相だけ合わせる、雰囲気だけ)。
   - 寄せる先は記録や記憶から写さず、実物を開いて測る。測るのは、地と文字の色、書体、ボタンの色と形。URL と測った日を記録に書く。
   - 使う組み合わせ全部 (文字と地、線と地) のコントラスト比を計算する。文字は 4.5:1、部品の境界と状態の印は 3:1 に届かない色を、直すか、飾りにだけ使うと役割を分ける。主操作の色は両方の基準を 1 色で満たすものにする。寄せる先が基準に届いていないときは、そのまま写すか基準を取るかを依頼者に聞く。
10. `DESIGN.md` を書く。下の骨組みを使う。依頼者が `DESIGN.md` を知らなければ、書く前に、企業が自分で公開している実物を 1〜2 個見せる。
    - 書くのは、まだ無い画面にも当てはまる決まりだけにする (下の「決定の行き先」)。
    - 製品の説明は依頼者に「この製品を一言で言うと何か」を聞いて書く。文書に 1 文で書かれていれば、それを見せて確かめる。聞いた答えの断片を継ぎ合わせて作らない。この先に広げる方向が決まっていれば、1 文で足す。
    - 決まったことは、決まったこととして書く。誰が決めたか、確認が済んだかは記録に書く。ルールの理由は人ではなく基本原則の名前に結び付ける。
    - 理由に基本原則を書けることと、依頼者が決めたことは別である。ルールごとの出どころ (依頼者の言葉、実物を見て承認、エージェントの推測) を記録に書く。推測から来たルールは、最初の実物を依頼者に見てもらうまで確定としない。
    - 実物がまだ無い節 (部品、影など) は書かない。
    - 骨組みの Layout と R-002 以降は、最初から決めて書く。エラーの色と、狭い画面の入力欄の文字の大きさも決める。無いと、最初の 1 か所を作る時点で判断が割れる。
11. 記録を書く。4 つの層 (制約、文脈、検証、フィードバック) の現状、決めたことと理由、今の画面で直す候補、決まっていないこと。
12. 足場を入れる。
    - トークンを、製品のコードが読む形にする。値の正は `DESIGN.md` に置く。数が多いか、変えることが多ければ、`DESIGN.md` から生成するスクリプトを作り、合っているかを確かめるオプション (`--check`) を付ける。数が少なく、ほとんど変えないなら、手で写してよい。その場合は、写した先に `DESIGN.md` が正だと書く。
    - 指示ファイルに 4 つを 1 行ずつ書く。UI を作る前に `DESIGN.md` を読むこと、トークンの CSS を直接編集しないこと、作った画面をヘッドレスで撮って自分で見ること、ルールに無い判断をしたら記録に書くこと。
    - 作り方の決まりも、`DESIGN.md` ではなく指示ファイルに書く。新しく書く箇所は新しい体系だけを使う、値を直接書かない、足した部品の見た目をトークンに直す、部品の置き場所。浮いて出るもの、ダイアログ、メニューは、自作する前に体系の部品を探す。書かないと、エージェントは位置の計算やキーの扱いを自分で書く。
    - 選んだ見た目の案を、見本の画像として記録の場所に置く。
    - 手順 3 で載せ替えると決めたときは、加えて次を行う (Tailwind と shadcn/ui の場合)。
      - 体系の既定の色、角、文字の大きさ、画面幅の区切りを消し、`DESIGN.md` のトークンだけを残す。トークンに無い名前は使えなくなる。
      - 既存の CSS は丸ごと 1 つの層に入れ、新しいクラスより弱い側に置く。層に入っていない CSS は新しいクラスより強く、`button` などの要素への指定が新しい部品の見た目を消す。
      - 要素の初期化 (preflight) は、既存の画面を移し終えるまで入れない。既存の画面がブラウザの既定の余白に頼っている。
      - 既存の CSS が文字の基準の大きさを変えているときは、余白の刻みを px で持つ。rem のままだと、大きさがすべて縮む。
      - 部品は公式の CLI で、使う箇所と一緒に足す。先に入れると、未使用の検査に落ちる。
13. 足場が既存の画面を変えていないことを確かめる。手順 12 で製品のコードを変えなかったときは省く。
    - 製品に既にある検査 (lint、型、未使用、テスト、E2E) を全部通す。落ちた検査が、その製品での共存の条件を教える。
    - 入れる前後で同じ画面のスクリーンショットを撮り、画素で比べる。差が出たら差の画像を見て、時刻や動きで変わる箇所だけかを確かめる。
14. 画面の 1 か所を、経緯を知らない別のエージェントに作り直させる。手順 14 から 16 が 1 周で、領域を変えて繰り返す。画面全体ではなく、一覧のような 1 つの領域にする。新しい領域は新しいエージェントに頼み、文書だけで前の領域とそろうかを見る。直しは同じエージェントに続けさせる。領域が 1 つしか無い小さな製品では、別のエージェントに頼まず自分で作り直してよい。その場合も、手順 15 と 16 は行う。
    - 頼む前に、その領域に何を載せ、どう動かすかを依頼者に決めてもらう。繰り返し出る小さな要素は、使い捨ての拡大の絵を見せて選んでもらう。絵と違う判断をするとき (基準を優先して外すものなど) は、作る前に伝える。
    - 頼む前に、作り直す範囲の「前」の画像を、状態ごとに自分で撮っておく。
    - 渡すのはリポジトリと依頼文だけで、依頼文には次を書く。
      - 作り直す範囲と、触らない範囲。
      - 先に、その範囲のテストの要素の指定を役割やラベルに直し、見た目を変える前にテストを通すこと。
      - 通す検査と、スクリーンショットを撮る幅と置き場所。
      - 禁止すること。コミット、窓の開くブラウザ、未コミットの変更を消す操作。
      - 見本と依頼文が食い違ったときに、どちらを取るか。
      - 新しい表示を足すときは、その情報が画面の手元にあるかを先に調べること。無ければ、取りに行く仕組みを足す前に報告すること。
      - 決めきれない扱い (要素どうしの重なり、端での見切れなど) は、凝った仕組みを作らず、起きる場面を画像に撮って報告すること。
      - 報告してほしいこと。沿ったルール、書かれておらず自分で判断したこと、迷ったこと、従えなかったこと、ルールに従った結果が変に見えた箇所。
15. 戻ったものを確かめる。
    - 報告された検査を、自分で再実行する。
    - スクリーンショットを自分で見る。大きさは書かれたクラスではなく、ブラウザの算出値で測る。
    - ルールに合っているかとは別に、ルールを忘れて、初めて見る人として変な箇所が無いかを見る。別のエージェントに画像だけを渡して批評させると補助になるが、依頼者が気づく違和感を見落とすことがある。依頼者の確認の代わりにはしない。
    - 依頼者に見てもらう。見る画像を 1 枚、見る範囲、聞くことを 1 つに絞り、今何をしていて、なぜ見てほしいかを添える。
16. 外れた箇所と、エージェントが挙げた判断を振り分ける。置き場所は下の「決定の行き先」で決める。振り分けた先を直してから、同じエージェントに読み直して合わせるよう頼む。次の回で同じ質問が出なくなったかで、ルールの効き目を確かめる。
    - ルールに従った結果が変だったときは、画面ではなくルールを疑う。エージェントはルールを正確に実行するので、間違ったルールはそのまま画面に出る。出どころを確かめ、推測なら書き直す。
    - 同じ独自の UI が 2 回出た: 部品にする。1 回なら記録に候補として残す。
    - 機械で判定できる違反: 検査の候補として記録に残す。
    - 見本と依頼の食い違いや、載せる情報の量: 依頼者に選択肢で聞く。
    - 画面から情報を外すときは、外す前に、その情報がほかの場所で見られるかを確かめさせる。
    - 道具の振る舞いはルールに書く前に実際に動かして確かめる。記憶や名前で決めない。
    - 周回のたびに `DESIGN.md` を読み返す。画面や機能の名前が入ったルールが増えていたら、依頼文と記録に移す。ルールの番号は詰めない。コードや記録から参照されている。
    - 部品を 1 つにそろえる変更は、すでに見てもらった箇所の見た目も変える。変わった箇所を依頼者に伝える。
17. 検査と部品の一覧を、選んで足す。どれも必須ではない。最初から全部は入れず、下の目安に当たるものが出たときに、入れるかどうかを依頼者に選択肢で聞く。省いたものは、理由と一緒に記録に書く。

    | 足すもの | 足す目安 | 省く目安 |
    |---|---|---|
    | 書き方の検査 (値の直書き、フォーカスの輪を消す指定、効かない名前のクラス) | 周回で同じ違反が 2 回出た。エージェントに繰り返し作らせる | 画面が少なく、作り終えたら変えない |
    | アクセシビリティの機械の診断 | ブラウザで動かすテストが既にある。操作できる部品がある | テストの仕組みが無い。その場合は、手で 1 回診断して済ませる |
    | CI への追加 | CI が既にあり、複数の人やエージェントが変更を入れる | CI が無い。1 人で作り、commit 時の検査で足りる |
    | 部品の一覧 (Storybook) | 部品を複数の画面で使い回す。部品の状態が多い | 1 枚のページや画面の少ないサイト。部品が数個で、コードを読めば足りる |

    - 検査は、周回で実際に出た違反から作る。新しい仕組みを入れる前に、製品に既にある道具 (スクリプト、commit 時の検査、テスト) に足す。
    - 足したら、わざと違反を入れて、落ちることを確かめる。
    - 外すしかない箇所は、理由を書いた印をその行に付けて外す。
    - 機械の診断は、作り直した領域に絞る。古い領域の違反で落ちないようにし、作り直すたびに対象へ足す。機械の診断は、目での確認とは別の違反を見つける。どちらも省かない。
    - CI に足したものは、手元で同じコマンドが通ることを確かめる。CI の上で動かしていなければ、未確認と書く。
    - 部品の一覧は、公式の手順で入れ、見本と使わない追加機能を入れない。製品の入口の CSS を読み込ませ、製品と同じ見た目にする。並べる状態は、実際の画面で起きるものだけにする。入れたら、製品の画面と一覧の画像を見比べる。
    - 部品の一覧を入れたら、指示ファイルに、部品や状態を足したときは一覧にも足すことを書く。起動は、ブラウザを自動で開かない指定にする。

**決定の行き先:** 基本原則の案、ルール、周回で出た決定のどれも、置き場所を次で決める。先に、その決定がまだ無い画面にも当てはまるかを確かめる。

- まだ無い画面にも当てはまる決定: 画面や機能の名前を使わない形に言い換えて、`DESIGN.md` のトークンかルールに書く。言い換えると元の意味が狭まるときは、元の言葉を記録に残す。
- その画面だけの決定 (何を載せるか、どう動くか): 依頼文に書く。作り終えたら、コードとテストを正とし、文書には写さない。決めた理由は記録に書く。
- 作り方の決まり (道具、コマンド、置き場所): 指示ファイルに書く。
