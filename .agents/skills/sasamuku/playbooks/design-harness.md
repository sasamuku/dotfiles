# Design Harness

**エージェントが UI を作っても品質がぶれない足場を、いちばん小さい形で製品に入れ、外した箇所から育てる。** 対象は、まだ足場が無い製品に最初の 1 周を通す依頼と、入れたあとに外した箇所を戻す依頼。判断は **principle-design-harness** と **principle-design-system** スキルに拠る。

依頼者に聞く、見せる箇所で答えが得られないときは、質問、仮の答え、外れたときの影響を記録に書いて進め、仮定として返信にまとめる。記録は `docs/design/harness.md` (既存の置き場所があればそちら) に書く。

1. 現状を調べる。4 つの層 (制約、文脈、検証、フィードバック) ごとに、ある / 人しか読めない / 無い を記録に書く。見るのは、`DESIGN.md` などのデザインの文書、トークン (CSS 変数や Tailwind の theme のように名前の付いた値)、部品とその一覧 (Storybook)、検査 (lint、テスト、CI)、指示ファイル (`AGENTS.md` / `CLAUDE.md`)。フロントエンドが部品を組み合わせて作る構成かどうかも書く。
2. 最初に入れるものを決める。下の表から、この製品に合うものだけを選び、正の場所と一緒に記録に書いて依頼者に見せる。
   - 基本原則 (製品の目的、人柄、設計で優先すること、避けること) が文書に無ければ、文書と依頼者の言葉から案を書き、質問にまとめて一緒に見せる。答えが得られなければ `DESIGN.md` には書かず、返信の未確認に、基本原則が空なのでルールに無い場面の判断がぶれると書く。
   - 正の場所は種類ごとに 1 つにする。判断の根拠とトークンの値は `DESIGN.md`、部品の実体と状態はコード。本番のコードにトークンが既にあり、`DESIGN.md` から書き出す形に変えないなら、本番を正とし、`DESIGN.md` の front matter には値を書かない。

   | 層 | 最初に入れるもの | 省くとき |
   |---|---|---|
   | 制約 | `DESIGN.md`。そのトークンを、本番のコードが読む形に書き出す | |
   | 文脈 | `DESIGN.md` の Overview と、指示ファイルから `DESIGN.md` への参照 1 行。いま使っている部品を、状態ごとに Storybook に載せる | 部品を組み合わせる構成でなければ Storybook を省く。エージェントが部品のファイルを直接読めるうちは MCP を省く |
   | 検証 | 機械の検査を 1 つ。トークンに無い色と余白の検出から始め、PR で動かす | CI が無ければ、手元で動くスクリプトまで |
   | フィードバック | 下の「育てる」を行うことと記録の場所を、指示ファイルに 1 行 | |
3. `DESIGN.md` を書く。下の骨組みを使い、既存の画面と文書にあるものだけを写す。
   - Overview には基本原則を書く。基本原則とルールは、依頼者に確かめたものか文書にあるものだけを書き、無い項目は行ごと省く。
   - トークンは色と文字を役割 (主操作、本文、背景、枠など) ごとに 1 つ、余白と角を 4 px の倍数の値から拾う。値は直さない。直したい値は記録の「直す候補」に書く。
   - `npx @google/design.md lint DESIGN.md` を通す。実行できなければ未確認と書く。
4. 入れる。手順 2 で選んだものを、次の順に 1 つずつ **feature** で入れる。
   1. トークンの書き出し。`npx @google/design.md export --format <形式>` (`css-tailwind`、`json-tailwind`、`dtcg` のどれか) か、front matter から CSS 変数を作るスクリプトを使う。書き出したファイルを本番のコードが読み込むところまでを行い、既存の値の置き換えはしない。受け入れ条件は、幅 375 / 768 / 1440 のスクリーンショットが前後で変わらないこと。
   2. 検査。既にある違反は、検査が読む一覧のファイルに書き出し、検査は違反が増えたときだけ落とす。違反が減ったら一覧を更新する。既にある違反の置き換えは、この作業に含めない。
   3. Storybook と、要るなら MCP。
5. 1 周させる。別のエージェントに、実際に要る小さな画面か変更を 1 つ作らせる。無ければ、既存の画面を 1 枚作り直させる。渡すのはリポジトリ (指示ファイルを含む) と依頼文だけで、ほかの補足をしない。出てきたものを検査に通し、スクリーンショットを自分で見て、外した箇所を記録に書く。作り直させた画面は確かめるためのもので、本番には取り込まない。ブラウザは画面に出さずに (ヘッドレスで) 動かす。
6. 外した箇所を、下の「育てる」で振り分ける。

**育てる:** 外した箇所や指摘が出るたびに行う。先に、題材が変わっても当てはまる「<条件> のとき <こうする>」に書き直す。書き直せないものはその画面だけの調整なので、入れない。

- 依頼者が方針として述べたこと: 1 回で `DESIGN.md` の Do's and Don'ts に入れる。
- 同じ種類の違反や指摘が 2 回出た: `DESIGN.md` の Do's and Don'ts に入れる。禁止には代わりに使うものを添える。
- 機械で判定できる: 検査にする作業を **feature** に渡す。
- 同じ独自の UI が 2 回出た: 部品にする作業を **feature** に渡す。
- 1 回だけ出た: 記録の「候補」に残す。もう一度出たら入れ、候補から消す。
- 入れないもの: 一般的な良し悪し、コードを読めば分かること、指示ファイルに既にある規約。

**`DESIGN.md` の骨組み:** 書式は [DESIGN.md の仕様](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) (Google Labs、alpha 版) に従う。無ければリポジトリのルートに作る。仕様にある節は見出しの名前と順序を変えず、書くことが無い節は見出しごと省く。わざと持たないトークンの種類 (`spacing`、`rounded`、`components` など) は、front matter の `omitted` に書く。値は front matter にだけ書き、本文ではトークンの名前で呼ぶ。`{colors.primary}` の形の参照は、front matter の `components` の中で使う。

````markdown
---
version: alpha
name: <製品名>
colors:
  primary: "<主操作の色>"
  on-primary: "<主操作の上の文字の色>"
typography:
  body-md:
    fontFamily: <書体>
    fontSize: 16px
spacing:
  xs: <最小の段階>
rounded:
  sm: <最小の段階>
components:
  button-primary:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.on-primary}"
    rounded: "{rounded.sm}"
---
````
