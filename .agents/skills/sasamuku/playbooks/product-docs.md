# Product docs

**製品の方向と要求を定める文書に責任を持つ。** なぜ作るかを書く Product Brief と、何を求めるかを書く PRD を、依頼者と合意できる形にまとめる。成果物はこの 2 つの文書で、設計と実装はしない。

各文書に何を書き、どこに置くかは **principle-product-docs** に従う。このプレイブックでは、依頼者に何を聞き、どの順で書いて出すかを決める。文書の雛形だけを頼まれたときは、下の「雛形を入れる」だけを行う。

1. **書く文書を決める。** PRD を頼まれて Product Brief が無いときは、方向が要求の前提になるので、Product Brief を先に書くかを依頼者に確かめる。PRD が既にあるときは、書き直すか、新しい版にするかを確かめる。新しい版にするなら、それまでのファイルを `product-requirements-document/v1.md` に移して新しい版を `v2.md` に書き、移したファイルへのリンクを直す。
2. **依頼者に聞く。** 既存の Issue、README、コードから書き起こさない。そこにあるのは作業の経緯で、製品の方向は書かれていないことが多い。依頼者が挙げた資料と、関係者と合意済みの文書は、書く前に原文を読む。書き起こしの材料にはしないが、書いた内容との差を項目ごとに示し、どちらに合わせるかを依頼者に確かめる。資料の内容を説明するときは、原文の該当箇所を引く。Product Brief を先に書くときと、先に書くかを依頼者に確かめているときは、最初の質問では Product Brief の項目だけを聞く。PRD の項目は、Product Brief を書いたあとに聞く。

   Product Brief では次を聞く。
   - 誰が提供し、どの事業の文脈にある製品か。
   - 誰が日々使い、誰が導入を決めるか。それぞれに何が響くか。
   - 最終的に目指す状態と、そこまでの登り方。
   - 作らないと決めていること。

   PRD では次を聞く。
   - 対象の開発段階と、その段階で確かめたいこと。
   - その段階でどこまでを目指すか。何が起きたら成功と言えるか。数値があれば、その根拠と合意先。
   - 必要な機能と、その優先度。今回は作らないもの。
   - まだ確かめていない前提と、その確認先。
   - 先に済んでいる必要があること。

   依頼者が開発段階と確かめたいことに答えられないときは、PRD は書かず、開発段階が決まっていないことを未決の判断として返す。説明に出た事業や関連製品は公開情報で調べ、説明と食い違う点だけを確かめる。
3. **書く。** **principle-product-docs** の雛形から作る。依頼者の説明にも既存の文書にも無く、推測で補った箇所には「（案）」と付ける。既存の構想や設計書と内容が重なるときは、役割の分け方を先に決める。
4. **重複を削ってから見せる。** 通して読み、セクションをまたいだ言い換えと、ほかの文書と重なる記述を消す。PRD を書いたときは、Product Brief と突き合わせ、2 つの文書のあいだに矛盾が無いことを確かめる。食い違いがあれば、どちらに合わせるかを依頼者に確かめる。
5. **「（案）」を消してから出す。** 「（案）」の箇所を依頼者に 1 つずつ確かめ、確定したら印を外す。確定できないものは本文から外し、未決の判断に移す。`grep -n "（案）" <文書>` が 0 件になるまで、マージしない。Product Brief と PRD を別の文書にしたときは、別の変更として出す。Product Brief は先に合意できることが多く、PRD の未合意の箇所に承認を止められずに済む。

**返信:** 文書の場所、自分の判断で書いた箇所、未決の判断。

## 雛形を入れる

1. 対象プロジェクトの指示と既存の文書を確かめる。文書の配置やテンプレートが既にあるときは、雛形の配置をそのまま採らず、どの構造にするかを依頼者に聞く。決めた構造に足りない分だけ補い、移動や上書きはしない。
2. **principle-product-docs** の `assets/docs/engineering/` を、指示ファイルも含めて対象プロジェクトの `docs/engineering/` に写す。依頼者と別の置き場所に決めたときは、そこに写す。ADR や Design Doc の中身は作らない。
3. 写した雛形を対象プロジェクトに合わせる。置き場所を変えたときは、雛形の中のパスとリンクも直す。API、DB、画面を扱わないと分かっているなら、補助テンプレートと、それを指す記述を外す。汎用の文書ガイドがあれば、ADR と Design Doc をその適用範囲外と明記する。指示ファイルが既にあれば、その管理方法を保ち、必要なルールだけ足す。テンプレートのコメントと記入例は残す。
4. 導入先の差分で、既存の文書が変わっていないことを確かめる。相対リンクと、`CLAUDE.md` の `@AGENTS.md` の参照先も確かめる。`NNNN` を含む記入例のリンクは除く。

**返信:** 置いたファイル、対象プロジェクトに合わせて変えた箇所。
