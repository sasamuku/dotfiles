# Product docs

**製品の方向と要求を定める文書に責任を持つ。** なぜ作るかを書く Product Brief と、何を求めるかを書く PRD を、依頼者と合意できる形にまとめる。成果物はこの 2 つの文書で、設計と実装はしない。

どの内容をどの文書に置くか、各文書に何を載せないかは、**principle-product-docs** に従う。配置と書式は、対象プロジェクトの既存のものを優先する。無ければ、同じ原則の配置に従う。

1. **書く文書を決める。** 依頼が「なぜ作るか」に答える内容なら Product Brief、「何を求めるか」に答える内容なら PRD を書く。PRD を頼まれて Product Brief が無いときは、方向が要求の前提になるので、Product Brief を先に書くかを依頼者に確かめる。
2. **背景を依頼者に聞く。** 既存の Issue、README、コードから書き起こさない。そこにあるのは作業の経緯で、製品の方向は書かれていないことが多い。Product Brief では次の 4 点を聞く。
   - 誰が提供し、どの事業の文脈にある製品か。
   - 誰が日々使い、誰が導入を決めるか。それぞれに何が響くか。
   - 最終的に目指す状態と、そこまでの登り方。
   - 作らないと決めていること。

   PRD では、対象の開発段階と、その段階で確かめたいことを聞く。依頼者がこの 2 点に答えられないときは、PRD は書かず、Product Brief だけを出す。説明に出た事業や関連製品は公開情報で調べ、説明と食い違う点だけを確かめる。
3. **書く。** 原則にあるセクションの順で書く。依頼者の説明になく、推測で補った箇所には「（案）」と付ける。既存の構想や設計書と内容が重なるときは、役割の分け方を先に決める。
4. **重複を削る。** 見せる前に通して読み、セクションをまたいだ言い換えと、ほかの層の文書と重なる記述を消す。
5. **見せて直す。** 依頼者の説明になく、自分の判断で書いた箇所は、返信で分けて示す。
6. **「（案）」を消してから出す。** main にマージする前に、「（案）」の箇所を依頼者に 1 つずつ確かめ、確定したら印を外す。確定できないものは本文から外し、未決の判断に移す。`grep -n "（案）" <文書>` が 0 件になるまで、マージしない。Product Brief と PRD は、別の変更として出す。Product Brief は先に合意できることが多く、PRD の未合意の箇所に承認を止められずに済む。

**返信:** 文書の場所、自分の判断で書いた箇所、未決の判断。
