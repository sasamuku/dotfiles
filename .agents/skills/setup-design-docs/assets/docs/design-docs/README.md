# Design Docs

機能・開発単位の設計を記録する。「なぜこの開発をするか」「何を作るか」「どう設計し、何を捨てたか」を実装前に書き、レビューを経て実装の拠り所にするのが目的。

## ADR との使い分け

| | [ADR](../adr/README.md) | Design Doc |
|---|---|---|
| 単位 | 意思決定 1 つ | 機能・開発 1 つ |
| 問い | 何を採用するか / どの方針にするか | なぜ作るか / 何をどう作るか |
| 例 | Linter に Biome を採用する | ページ編集と自動保存の設計 |
| 更新 | 不変（変更は新 ADR で置き換え） | 生きた文書（追記・補足を優先） |

迷ったら: 独立した決定 1 つなら ADR、機能のまとまりなら Design Doc。Design Doc を書く過程で生まれた横断的な決定（データ設計方針・認証方式 など）は ADR に切り出し、Design Doc からリンクする。

## いつ書くか

実装に入る前に設計の合意を取りたい開発をするとき。例:

- 新しい機能のまとまり（例: ページ編集、リンク抽出、認証）
- 複数の画面・API・テーブルにまたがる変更
- 却下した代替案を残しておきたい設計

軽微な変更や、コードを読めば自明なものは書かなくてよい。

## 配置場所と番号付け

Design Doc 1 つにつきディレクトリ 1 つを作る。番号は既存の最大 + 1、4 桁ゼロ埋め（ADR と同じ）。

```
docs/design-docs/
├─ TEMPLATE/         # 雛形一式（記入例付き）
├─ 0001-短いタイトル/
│  ├─ README.md      # 本体
│  ├─ database.md    # 補助: テーブル定義・クエリ設計（不要なら削除）
│  ├─ api.md         # 補助: エンドポイント定義（不要なら削除）
│  └─ screens.md     # 補助: 画面構成・遷移（不要なら削除）
└─ ...
```

## 書き方

1. 次の番号を採番し、`TEMPLATE/` をコピーする。不要な補助ファイルは削除する。
   ```sh
   cp -r docs/design-docs/TEMPLATE docs/design-docs/0001-page-editing
   ```
2. 中身を書き、`ステータス` を `Draft` にしてレビューに回す（PR の要否はプロジェクトの運用に従う）。
3. レビューで合意できたら `Accepted` に更新し、実装に入る。
4. 実装完了後、`Implemented` に更新する。実装中に設計が変わったら Design Doc に追記して差分を残す。

## ステータス

- **Draft**: 執筆・レビュー中。
- **Accepted**: 合意済み。実装の拠り所となる。
- **Implemented**: 実装完了。以後は記録として参照。
- **Superseded**: 別の Design Doc に置き換えられた。置き換え先へのリンクを添える。

## 運用ルール

- **追記優先**。ADR と違い生きた文書だが、意思決定の経緯が追えるよう、合意済みの内容は消さずに追記・補足で更新する。
- ファイル名の番号は再利用しない。欠番になっても詰めない。
