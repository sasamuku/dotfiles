# Architecture Decision Records (ADR)

技術選定や設計上の重要な意思決定を記録する。「なぜそうしたか」を後から辿れるようにするのが目的で、実装の詳細ではなく **決定とその背景** を残す。

## いつ書くか

後から「なぜこうなっているのか」を問われうる決定をしたとき。例:

- 技術・ライブラリ・ツールの採用 / 不採用（例: Linter に何を使うか）
- アーキテクチャ構成の選択（例: モノレポ構成、BFF の分離）
- 一度決めたら覆しにくい方針（データ設計方針、認証方式 など）

軽微な決定や、コードを読めば自明なものは書かなくてよい。

## 書き方

1. 次の番号を採番する（既存の最大番号 + 1、4 桁ゼロ埋め）。
2. `TEMPLATE.md` をコピーして `NNNN-短いタイトル.md` を作る。
   ```sh
   cp docs/adr/TEMPLATE.md docs/adr/0001-linter-formatter.md
   ```
3. 中身を書き、`ステータス` を `Proposed` にしてレビューに回す（PR の要否はプロジェクトの運用に従う）。
4. レビューで合意できたら `Accepted` に更新する。

## ステータス

- **Proposed**: 提案中。レビュー・議論の対象。
- **Accepted**: 承認済み。現在有効な決定。
- **Deprecated**: 廃止。もう有効でないが記録として残す。
- **Superseded**: 別の ADR に置き換えられた。置き換え先へのリンクを添える。

## 運用ルール

- **ADR は不変（immutable）**。一度 Accepted になった内容は書き換えず、方針が変わったら新しい ADR を起こし、古い方は `Deprecated` / `Superseded` にする。
  - 誤字修正など、決定内容に影響しない軽微な編集は除く。
- ファイル名の番号は再利用しない。欠番になっても詰めない。
