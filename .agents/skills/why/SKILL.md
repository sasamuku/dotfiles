# Why

分かったことと、推測したことを分けて伝える。それがこのスキルの価値である。

## 進め方

1. **対象を決める。** どのコードの、何の理由を知りたいのかを 1 文で書く。曖昧なら、開いているファイルや直前の話題から推測し、その解釈を書いて進める。
2. **手がかりを集める。** 対象のファイルと行を決め、次で履歴をたどる。
   - `git blame -L <開始>,<終了> <file>`: 最後に触ったコミット
   - `git log --follow -p -- <file>`: 名前の変更をまたいだ履歴
   - `gh pr view <番号> --json title,body,comments,reviews`: PR の説明と議論
   直近のコミットだけで判断しない。今の形は、過去の判断の積み重ねであることが多い。
3. **情報源を広げる。** Git と PR のほかに使える情報源 (Issue、ドキュメント、Slack、Sentry など) があれば、情報源ごとにサブエージェントを同時に起動して調べさせる。ファイルは編集させない。各サブエージェントには、検索したこと、見つけた証拠、矛盾、見つからなかったことを返させる。
4. **まとめる。** 主張ごとに、下の確信度を付ける。

## 情報源ごとの探し方

| 情報源 | 探すもの |
|---|---|
| Git / PR | コミットメッセージ、PR の説明とレビューコメント、コードコメント、テスト |
| Issue | 背景にある要望や不具合、リンクされた PR |
| ドキュメント | 設計書、ADR、ポストモーテム |
| Slack など | ドキュメントにならなかった議論 |
| Sentry など | 防御的なコード (null チェック、リトライ、タイムアウト) の原因になったエラー |

対象のコードが防御的に見えるときは、障害対応で足されたものではないかを疑い、「revert」「hotfix」「障害」などを含むコミットや議論を探す。

## 確信度

| 確信度 | 意味 | 書き方 |
|---|---|---|
| 確実 | 作者が理由を明記している (PR、Issue、コメント) | 引用を付けて言い切る |
| 有力 | 明記はないが、複数の証拠が同じ結論を指す | 証拠を並べて「〜と見られる」 |
| 推論 | 文脈からの解釈 | 「A と B から、C の可能性が高い」と根拠をつなげて書く |
| 推測 | 証拠が薄く、他の説明もあり得る | 「可能性の 1 つは X。直接の証拠はない」 |
| 不明 | 調べたが分からない | 何を検索したかを具体的に書く |

証拠なしに「〜のために設計された」「チームが決めた」と書かない。

## 書き方

次の順で書き、当てはまらない節は省く。

- **問い**
- **判明したこと** (確実、有力)
- **推論できること** (推論)
- **競合する仮説** (推測を並べる)
- **分からないこと** (不明。検索した内容も書く)
- **参照した情報源** (何も見つからなかった情報源も、理由とともに書く)

この調査がコード変更の前段なら、最後に「残すべきもの / 変えてよいもの / 避けるべきもの / リスク」を短く添える。
