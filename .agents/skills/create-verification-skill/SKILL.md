# Create verification skill

対象: $ARGUMENTS (省略時は作業中のリポジトリ)。

アプリを起動し、利用者と同じ経路で操作して、証拠を残す検証スキルを、対象リポジトリに作る。読むのは人ではなく、このアプリを初めて見るエージェントで、作業の途中で参照する。

## 1. リポジトリから調べる

次をコードから調べ、コードから分からないことだけを利用者に聞く。

- 利用者が触るもの: Web 画面、CLI や TUI、デスクトップ、API、モバイル、ライブラリ。複数あれば主なものを選び、残りを書き留める。
- 起動: リポジトリが文書にしている開発用のコマンド。ポート、環境変数、初期データ、認証。
- 操作の手段: 既存の仕組み (Playwright のテスト、curl で叩けるエンドポイント、デバッグ用のポートなど) を先に使う。無ければ、Web と Electron はブラウザ、CLI と TUI は tmux や PTY、サービスは HTTP で操作する。
- 証拠: スクリーンショット、端末の記録、応答の本文、ログ、終了コード、DB の状態。
- 分離: 検証用のインスタンスを 2 つ同時に起動できるか (ポート、データディレクトリ、プロファイル)。

そのままでは起動できないなら、先に直すか、何が足りないかを正確に報告する。壊れた状態に合わせて書いたスキルは、誤った手順を教える。起動を妨げているのが検証に関係しない欠落 (API が使わない静的ファイルのディレクトリ、サンプルの設定など) なら、検証用の足場と明記して作り、後片付けで消す手順にしてよい。

## 2. 検証スキルを書く

`.agents/skills/verify-<app>/SKILL.md` に書き、`.claude/skills/verify-<app>` から symlink を張る。フロントマターには `name: verify-<app>` と、アプリ名、利用者が触るもの、使う場面が分かる `description` を入れる。フロントマターが無いとスキルとして登録されない。本文は調べて分かった実際の値で書き、仮の値を残さない。次の節をこの順で書く。

- 起動: 空のデータから使える状態になるまでのコマンド (マイグレーションと初期データを含む) と、準備ができた合図 (ログの行、プロンプトなど)。プロセスが応答するだけでは、準備ができたとはみなさない。インスタンスを 2 つ同時に起動できないなら、そう書き、共有のインスタンスは操作せずに断るよう書く。短命な CLI なら、ビルドを 1 回だけ行い、操作のたびに別の PTY か tmux のセッションで起動する。
- 点検: 読み取りだけで「このインスタンスを操作してよいか」を確かめるチェックを 1 つ。プロセス、ビルドのバージョン、ポートの持ち主、認証を見る。様子がおかしいときは、まずこれを走らせる。
- 操作: このリポジトリに実在するセレクタやコマンドで書く。座標やタブの順番ではなく、ARIA ラベル、data 属性、プロンプトの文字列、ルートのパスのような変わりにくい目印を使う。
- 証拠: 何を残すかと、その置き場所 (`artifacts/<機能>/` など)。次を基準にする。
  - 利用者と同じ経路で操作する。内部の setter やテスト専用のエンドポイントを使わない。
  - 操作と、その結果の状態を両方残す。最後の画面だけでは足りない。
  - 画面に見えない副作用 (書いたファイル、増えた行、送ったメッセージ) も確かめる。
  - モックは本番でも外部と切り離されている境界にだけ使う。
  - dry-run やテストモードは名前を信じない。ファイル、ネットワーク、git の ref を観察し、本当に何を飛ばすかを確かめる。
- 後片付け: 自分が起動したものだけを止める。プロセス名で止めない。証拠は消さず、決めた置き場所に残す。
- 補助スクリプト: 実行権限を付け、呼び方を本文に書く。

## 3. 機能の地図を作る

`verify-<app>/features/` に、索引の `README.md` と、利用者が使う機能ごとに 1 ファイルを作る。まずはルート、コマンド、メニュー、文書から、主な機能を 3〜5 個選ぶ。

`README.md` には次を書く。

- 共通の前提: 起動先、実行ごとに分けた使い捨てのデータ、初期データ、点検。
- 操作の決まりと証拠の基準: 証拠には機能の ID と使った入口を添える。ある入口を飛ばしたなら、別の入口で確かめたことを、その入口の検証済みとして報告しない。
- 地図を、このリポジトリの検証で参照する資料とすること。入口が複数ある機能で、1 つしか操作していない確認は不完全とみなす。
- 機能を変えたら、該当する機能ファイルも直すこと。
- 機能の索引。

機能ファイルは H1 と、利用者から見た振る舞いを 1 段落で書く。続けて、次の 4 つの H2 をこの順で書く。例は [references/feature-example.md](references/feature-example.md)。

1. `サブ機能`: 短い ID と、それぞれの振る舞いを 1 行で。
2. `たどり着き方 (利用者の視点)`: 入口をすべて。
3. `<操作の道具> での操作`: 道具は 1 で選んだ操作の手段 (例では `control-notes`)。`前提:` から始め、手順ごとに 1 項目で、利用者の操作、実際のコマンド、見えるはずの結果の順に書く。
4. `落とし穴`: 検証を無駄にしたり、誤らせたりする罠。

地図には利用者の経路、目印、必要な状態、コマンド、見える証拠だけを書き、実装の詳細は書かない。初期データが足りず確かめられない機能は、失敗として報告する。手順を甘くして通してはならない。理由は `落とし穴` に書く。

## 4. 渡す前に 1 回通す

生成したスキルの手順どおりに、次を最後まで行う。

- 起動
- 点検
- 地図にある機能を 1 つ操作する
- 証拠を取る
- 後片付け

後片付けのあとも、証拠が決めた置き場所に残っていることを確かめる。失敗したら直し、失敗した試行のあとにも後片付けを走らせて、プロセスやポートを残さない。一度も実行していない検証スキルは下書きとみなす。

検証スキルを実際に使う環境とは別の環境 (新しい VM の代わりのコンテナなど) で通したときは、その環境でだけ行った準備の手順を挙げ、実際に使う環境で通すまで未検証として残す。

## 5. 返す

作ったファイル、1 回通した結果と証拠の場所、確かめられなかった機能とその理由を返す。通せなかった手順があれば、その原因も返す。
