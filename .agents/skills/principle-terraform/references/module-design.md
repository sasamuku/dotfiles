# module の設計

root module は組み立てに専念し、機能の中身は child module に置く。root は環境ごとに薄く作り、共通の child module を呼び出して、ある module の output を別の module の input に渡す。module のツリーは 1 階層に保ち、child から別の module を呼ばない。

こうすると、環境の違いは root だけに現れ、機能の中身は環境をまたいで 1 か所で持てる。child module は自分がどの環境で使われるかを知らずに済むので、単独で読め、単独で試せる。

## 3 つの境界

構成の分け方は、次の 3 つの境界を別々に考える。1 つの境界を決めた理由で、別の境界を決めない。

| 境界 | 分ける理由になるもの |
|---|---|
| 環境・アカウント | 隔離の要件、認証情報、環境ごとの違い、環境を足すときの再利用 |
| root・state | 独立した plan と apply、ライフサイクルの違い、変更の影響範囲、復旧、権限 |
| child module | 1 つの機能としての責務、一緒に変わる resource、公開する入出力、再利用先 |

module の分割と state の分割は、別の判断である。state を分けると、state 間で値を受け渡す方法と、構築・更新・復旧の順序を考える負担が増える。

## 判断の観点

- **環境の違いは root で吸収する**: 環境ごとの分岐を child に散らさない。root が構成を選び、容量や保持期間などの値を child に渡す。依存先が作成済みか新規かの違いも、呼び出し側で吸収する。child は「取得するか作成するか」の分岐を持たない。
- **provider と backend は root に置く**: child は必要な provider を宣言するだけにし、alias は明示的に受け取る。provider の設定を持つ module は、`count`、`for_each`、`depends_on` と一緒に使えなくなる。
- **機能と付随物は同じ child に置く**: 機能の本体と、その権限、ログ、イベントの接続を同じ child にまとめ、policy の持ち主を 1 つにする。root に残すのは、機能をまたぐ接続だけである。
- **依存は参照でつなぐ**: 循環を避けるために、ID や名前を文字列で組み立てない。参照を切ると依存グラフが失われ、作成と削除の順序が保証されなくなる。module 同士が参照し合っているだけでは、循環とは限らない。
- **入力は絞る**: 入力には型、説明、検証を付ける。設定を object に詰めて丸ごと渡さない。安全な既定値と必須入力を区別する。
- **module の大きさは数で決めない**: 機能のまとまりと入出力で決める。単一 resource のラッパー、何でも包む巨大な module、設定を丸ごと渡すだけの module は、どれも境界として働かない。module の数に上限は無い。ファイルの分割は module の境界ではない。定義の数や行数は、`count` や `for_each` を展開した後の resource の数とは別物であり、分割や規模の根拠にならない。
- **動いている module は残す**: 原則に合わせるためだけに、機能している既存の module を作り直さない。

## 適用範囲と例外

新しく構成を設計するとき、既存の構成を見直すときに当てはまる。上の形は出発点である。既存の方式や要件に別の形が合うなら、その形でよい。ただし、出発点と比べて、なぜその形を選ぶのかを説明できることが条件である。

環境の数、state の数、module の切り方、repo の分け方は、そのプロジェクトの要件から決まる。過去のプロジェクトや参照資料での個別の判断は、共通の決まりではない。

## 事例

| 悪い例 | 良い例 |
|---|---|
| 1 つの root にすべての resource を並べ、環境ごとに root を丸ごと複製する | 環境ごとの薄い root から、共通の child module を呼ぶ |
| child の中で `var.env == "prod"` を見て、resource の有無や大きさを変える | root が環境ごとに値を決め、容量や有効にするかを child の入力として渡す |
| child の中で data source を使い、VPC が既にあれば取得し、無ければ作る | 呼び出し側が VPC を用意し、その ID を child の入力として渡す |
| child の中に provider ブロックを書く | root で provider を設定し、alias が要るときは `providers` で明示的に渡す |
| `aws_s3_bucket` 1 つだけを包んだ module | バケットと、その policy とログの設定を、1 つの機能としてまとめた module |
| 循環を避けるため、ARN を `"arn:aws:iam::${var.account_id}:role/app"` と文字列で組み立てる | 作った module の output を参照して渡す |
| ネットワークとアプリの module を分けたので、state も同じ単位で分ける | state を分けるかは、ライフサイクルと復旧の手順を比べて別に決める |
