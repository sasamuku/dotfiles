# Close Issue

会話で作業してきた Issue を、本文を実態に合わせて整えてからクローズする。作業内容と結果は会話で把握しているものを使い、**read-issue** での読み直しはしない。把握できていない事実だけを PR やコミットで確かめる。

## 本文を整える

更新の直前に現在の本文を取得し、他者の編集を上書きしない。変えるのはチェックの状態と、事実が変わった箇所だけにする。背景や他者の要望・経緯は残す。

- 達成した項目のチェックボックスにチェックを付ける。途中で取りやめた作業は達成に数えない。
- 作業の途中で変わった方針・範囲・手順など、古くなった記載を実際の結果に合わせて書き換える。別の作業に置き換えた項目は、実際に行った内容に書き換えてチェックを付ける。他者が書いた記載は消さずに、現状を注記する。
- 未達の項目は消さず、チェックも付けない。対応しなかった理由か移管先を書く。

## クローズする

GitHub のクローズ理由 (completed / not planned / duplicate) は、実際の結果に合うものを選ぶ。

クローズのコメントは、整えた本文とクローズ理由を読んでも、なぜ閉じたかが分からないときだけ書く。次のような場合である。

- 完了条件を満たさないまま閉じる。
- 対応しないと決めた。
- 別の Issue に移した、または重複していた。

書くときは、閉じた理由を端的に書く。本文に書いてあることは繰り返さない。完了条件をすべて満たして閉じるときは、コメントを書かない。

完了条件が求める手順や確認先の記録は、クローズのコメントではなく、作業記録のコメントか本文に置く。

## 報告

Issue へのリンクと本文の変更点を示す。クローズのコメントを書いたときは、それも示す。
