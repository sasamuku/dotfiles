# Anything Else

対象: $ARGUMENTS (省略可)。

## 対象を絞る

会話から今回の目的・完了条件・未完の約束を確認し、今回の変更・操作に関係する範囲を調べる。

候補ごとに「今回の目的との関係」と「対応しないと何が困るか」を確認し、具体的な根拠があるものだけ提案する。短時間でできることや、一般に望ましいことだけでは提案しない。

- main の同期、マージ済み worktree・ブランチの整理、古い stash などは、今回の目的への具体的な支障か、明示的な確認依頼がある場合だけ対象にする。
- 既存 issue で追跡済みで状況が変わっていない残件や、今回と無関係な改善事項は再掲しない。ただし、今回の完了条件を満たすために必要な残件は省かない。
- 意図して残したプロセスやデータを後片付けの対象にしない。作成者・用途・今回との関係が不明なものを、残っているだけで操作候補にしない。

## 確認

対象に応じて必要な情報だけ確認する。

1. **会話・成果物**: 依頼の未対応、成果の未反映、必要な検証の抜け、未回答の懸念
2. **git**: 今回の差分・コミットの保全や反映、一時退避した編集の戻し忘れ
3. **issue / PR**: セッションで触れたものの完了条件・記録と実態の整合
4. **プロセス・規約**: 今回起動したものの残存による支障、今回に適用される必須の後処理

## 出力

残件を次の区分で示す。各項目に通し番号を付け、根拠と対応しない場合の支障を簡潔に添える。空の区分は省略する。

- **今必要**: 今回の完了条件が未達のもの、未完の約束、放置すると具体的な支障が出るもの。成果の反映・検証を事務的な整理より優先する。
- **待ち・後で対応**: 必要だが外部対応や判断を待つもの、対応時期を分ける合意があるもの。待ちの理由・再開条件と、既存の追跡先があれば示す。起票は必要な継続作業に限って提案する。

残件がなければ「追加対応なし」とし、確認範囲を短く添えて終える。問題のなかった観点を一項目ずつ列挙しない。

## ルール

- 提案のみ。実行は番号で承認を得てから。issue / PR 作成は `create-issue` / `create-pr` に従う
- 削除系 (worktree・stash・ブランチ) は対象と中身の有無を明示し、個別に承認を得る
- 確認していない観点を「問題なし」に書かない
