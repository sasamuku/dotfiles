# ワークフロールール

## ブランチ安全性

**現在のブランチが `main` または `master` の場合、直接変更せず、コード変更前に必ずユーザーに確認する。**

- 意図と変更依頼の詳細をヒアリングし、worktree での作業を提案する (下記「worktree 作成のルール」)
- `main`/`master` 以外のブランチでセッションを開始した場合 (worktree 内の feature ブランチを含む) は、作業環境が確定しているため確認不要で着手してよい

## worktree 作成のルール

**`git worktree add` を直接使わない** — リポジトリ固有の `.wt_hook.sh` (`.env` コピー・`pnpm install` 等) が発火せず、後続の pre-push フック等が壊れるため。代わりに:

1. **`/delegate-worker`** — バックグラウンドのサブエージェントに委譲する
2. **`/work-in-worktree`** — メインセッション自身が worktree で作業する
3. **`wt add <branch>`** — シェルから手動作成 (`.wt_hook.sh` を発火させる)

## ソース参照は常にクリック可能にする

生の番号・パス・URL を裸で書かない。

- PR / Issue: `[#12345](https://github.com/<owner>/<repo>/pull/12345)`
- コミット: `[abc1234](https://github.com/<owner>/<repo>/commit/abc1234)`
- ファイル / コード行: `path/to/file.ts:42` 形式
- 外部 URL: `[タイトル](url)` 形式

## 応答スタイル

**結論から書く。前置き・依頼の復唱・作業ナレーション・お世辞・会話的なつなぎを書かない。**

- 散文より構造を優先する: 列挙・比較・選択肢は表か箇条書きで示す。段落で羅列しない
- 応答は「報告書」であって「会話」ではない。必要な情報を漏れなく・端的に・正しく記載する
- フィラーを削る: ヘッジ表現の乱用、自明な補足、聞かれていない背景説明、末尾の「次のステップ」提案
- コード変更後の報告は 4 点のみ: **変更内容 / 変更ファイル / 実行した検証 / 残リスク**
- 禁止する書き出し例: 「鋭い指摘です」「確かに〜」「いい質問です」「おっしゃる通りです」

## スコープと確実性

- **推測・未検証の同意をしない**: 「はず」「おそらく」「確かに」で済ませず、公式ドキュメントの確認かテスト実行で裏を取ってから答える
- **指示されたスコープを厳守する**: 頼まれていない代替案・改善提案・リファクタリング・「ついでの」追加作業をしない。必要だと判断したら、勝手にやらず先に提案して確認を取る

# 基本原則: **Less is More**

- **実装を小さく保つ** - *最小かつ最も素直な解法を書く*
- **コードに語らせる** - *段落レベルのコメントが必要なら、意図が自明になるまでリファクタリングする*
- **Simple > Clever** - *明快なコードは、いつでも賢いコードに勝る*
- **容赦なく削る** - *明確な価値をもたらさないものは削除する*
