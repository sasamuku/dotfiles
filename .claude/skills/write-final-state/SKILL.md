# Write Final State

永続化するテキストには**最終的な決定事項だけ**を書く。そこに至る変遷は書かない。

作業中は「A を試して B になった」という経緯が頭にあるため、それが自然な説明に見える。しかし読者にとって A は存在しない。A への言及は、読者が知らない選択肢を説明され、なぜそれが否定されたのかを考える負担になる。

変遷は commit message・PR・ADR が持つ。ドキュメントとコメントは現在の状態を述べる。

## 対象

| 対象 | 扱い |
|---|---|
| README・設計ドキュメント・コードコメント・設定ファイルのコメント | **最終状態のみ** |
| commit message・PR 本文 | 変更内容を書く (差分がその役割) |
| ADR・意思決定ログ | 経緯を書く (それが目的) |

ユーザーが「経緯も書いて」と明示したときは従う。

## 検出パターン

書いた文が次に当てはまるなら、経緯が混入している。

| パターン | 例 |
|---|---|
| **否定形の対比** | 「A ではなく B を使う」「A ではないので B」 |
| **時制のある変更** | 「〜していたが」「〜に変更した」「〜をやめた」「もともとは」 |
| **暫定性の表明** | 「今のところ」「当面は」「一旦」「暫定的に」 |
| **不在の理由づけ** | 「A は使わない」「A は入れていない」(A が候補だったことが前提) |
| **履歴的な追記** | 「〜を追加した」「新しく〜」「従来の〜」 |

判定基準は 1 つ。**その文から読者が「かつて別の状態があった」と読み取れるなら書き換える。**

### 書き換えないもの

同じ語形でも、対比する相手が**現在も存在する別物**なら経緯ではない。そのまま残す。

| 残す | 理由 |
|---|---|
| 本文ではなく冒頭 200 文字を返す | 本文と冒頭は今も両方ある。仕様の対比 |
| 共有は義務ではなく選択肢 | 概念の定義。義務だった時期があるわけではない |
| 存在を漏らさないため 403 ではなく 404 | 403 は実在する別の応答。設計の説明 |
| 検出ではなく修正を担わせる | 検出は CI が今も担当。役割分担の説明 |

過去の状態を指しているのか、並存する選択肢を指しているのかで分ける。

## 書き換え

否定を消し、対象そのものの性質として述べる。

| 経緯が混入 | 最終状態 |
|---|---|
| 開発用の `daku` ではなくテスト専用の `daku_test` を使う | テストの接続先は `daku_test` |
| npm ではなく pnpm を使う | パッケージマネージャは pnpm |
| 以前は同期処理だったが、今は非同期で実行する | 非同期で実行する |
| 暫定的にインメモリで保持している | インメモリで保持する |
| REST をやめて GraphQL にした | API は GraphQL |

理由が必要なら、**選んだものの性質**で説明する。

```
✗ トランザクションだと service 側と二重になるため、DB 名で分ける
✓ テストは各ケースの前にテーブルを空にするため、接続先を専用 DB に分ける
```

「A だと困るから B」は A の知識を要求する。「B はこういう性質だから B」は B だけで完結する。

## 適用のタイミング

- ドキュメント・コメントを**書いた直後**に、上の検出パターンで自分の文を読み返す
- 既存ファイルを**編集するとき**、触った箇所の周辺に同じパターンがあれば併せて直す
- 方針が変わった直後に書く文は特に混入しやすい。「さっきまで A だった」という記憶が文に出る
